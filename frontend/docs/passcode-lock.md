## Passcode Lock (app-level gate + web key wrapping; RELEASED — merged to master `d446a9d` 2026-09-06, live as 0.2.22)

- **Departures and returns (2026-09-06, from the owner's phone tests of the branch builds 0.2.17–0.2.22).** Three facts the unit suite could not see and the Pixel_7 emulator proved: (1) on wake Flutter web delivers `hidden → inactive → resumed`, and `MainShell` rightly treats `inactive` as a departure — so `PasscodeProvider` stamps a departure ONCE (`_away`, cleared by every foreground verdict and by a lock; the latch guards the STAMP only, the 0 s verdict still runs on every signal) or the wake re-stamps `passcode_last_active_at` at the wake instant and a 15-minute screen-off comes back unlocked. (2) On wake the browser re-shows the LAST PAINTED frame before any code runs, and a real screen-off leaves 81–397 ms between `blur` and hidden — not enough for a Flutter frame — so the privacy curtain is a DOM element (`#fp-curtain` in `web/index.html`, shown synchronously by the page's own blur/visibilitychange handler while `armDomCurtain(true)`, and at boot when `localStorage.flutter.passcode_enabled` is `true` so a lock's relaunch never paints white). Dart LIFTS it from `PasscodeGate` in a post-frame callback only after a frame that paints what replaces it; lifting before the return verdict flashes the chat. `PasscodeCurtain` (Flutter) covers `unknown` and the Flutter-level `curtained` state and paints OVER the app, never Offstage (a pending `<input type=file>` lives there). A Flutter-only curtain was built first and FAILED the burst-screenshot proof — setting state is not painting a frame. (3) The attach picker span (`composerNativePickerActive`) — and, since amendment (lxxvi) clause 2, a live link ceremony (`linkCeremonyActive`), which `PasscodeProvider._departureExempt()` treats identically — is exempt from the immediate lock, the foreground verdict AND both curtains: its sheet hides the page, and locking (web: relaunching) or curtaining there loses the pick or flashes the composer. Verify any change here the way it was proven: real screen-off on the emulator (`KEYCODE_SLEEP`), burst `screencap` on wake, classify by pixel AND read visually — the pixel heuristic misread once.
- **Rollback rule while wrapping exists:** a bundle without `fpwk1:` unwrap code must never be served to a browser with the passcode ON (the envelopes read as garbage — the identity-loss shape). Every master build now carries it; the rule matters for any future branch test that predates §10a.

### 10a. Phase 2 — the passcode as key material (web only)

- **Only the KEYS are wrapped, never the sealed rows.** `services/encryption/content_key_wrap.dart` wraps the 32-byte `fp_sig_key_<kid>` / `fp_content_key_<kid>` values as `fpwk1:<kekId>:<b64 sealed>` under a passcode-derived KEK (PBKDF2-HMAC-SHA256, 600k, its OWN salt — never the verifier's, so the stored verifier is not a crib). The `fpsig1:`/`fps1:` row envelopes and every key NAME stay in clear, because the sealed-store open probe counts rows by that cleartext prefix (`sealed_web_signal_kv.dart`) and `_hasPriorInstallResidue` scans names only (`encryption_service.dart`) — encrypting either one makes a locked device look like a fresh install and mints a new Signal identity. That is the 0.1.10/0.1.11 catastrophe, reachable by encrypting a five-character prefix.
- **`KeyInventory.lockedKeyCount` is the third state that makes it safe.** Before Phase 2, any value that was not 32 raw bytes was silently DROPPED, so a locked device read as a device with NO keys — and no keys + no sealed rows mints a fresh key or falls back to plaintext. Locked now outranks the sealed-row probe in BOTH stores: `SigSealOpenUnavailable('locked', fallbackLegal: false)` and `ContentStoreUnavailable('locked', locked: true)`, the latter rethrown by `content_kv_opener_stub.dart` instead of degrading to `PrefsContentKv` (falling back there would write the decrypted-message cache in cleartext while the app is locked). `mintContentKey` refuses while locked, and refuses only when wrapping is actually ON — `isWrappingOn()` (a meta record, not `isLocked`), or every user without a passcode would be unable to mint at all.
- **Meta record FIRST, keys after.** `enableWrapping` writes `fp_passcode_kek_meta_v1` (kekId + iterations + salt, so the cost factor can be raised later) before `wrapRawKeys` converts anything. Interrupted that way, the device is merely LESS protected (raw keys still readable) and the next unlock resumes; the opposite order leaves envelopes whose KEK can never be re-derived, i.e. unreadable history and only the erase as a way out. `wrapRawKeys` is armed (write → read back → prove it unwraps) and rolls a key back to raw if it cannot prove that, and it is idempotent so every unlock is a resume point. `unwrapAllKeys` runs BEFORE `disableWrapping`; `rekey` (a passcode change) goes wrapped → raw → wrapped so an interruption leaves keys readable.
- **A wrapped device boots LOCKED regardless of the auto-lock window** (`PasscodeProvider.initialize`): the KEK is RAM-only, so a fresh process cannot read the key material however recently the app was used. `PasscodeUnlockGate` (`services/passcode_unlock_gate.dart`) holds `_initializeE2EInner` after the boot markers and before `_encryptionService.initialize` — open by default, so a device without a passcode is unchanged, and an already-initialised session never waits (a reconnect while the UI is locked must still do its housekeeping).
- **A mid-session re-lock is a REAL revocation on web (2026-09-04), not a UI barrier.** `_lock()` does three things in order: drop the KEK (zeroed before the reference goes, because the sealer memoizes its imported `AesGcmSecretKey` in an `Expando` keyed on that exact byte list) and close the gate; then, with wrapping on, `E2eLockRevoker` (`services/e2e_lock_revoker.dart`) tears the live stack down — `SealedWebSignalKv.revoke()` and `SealedWebContentKv.revoke()` forget their keys AND the content store's `_view`/`_unsealMemo`, which held the PLAINTEXT of every sealed row read this session, `EncryptionService.revokeForPasscodeLock` drops the in-RAM Signal identity and both store memos, and `EncryptionProvider` drops `_decryptedContentCache`; then on web `relaunchApp()` (`utils/app_relaunch.dart`) replaces the process, because the message list, the conversation previews and the rendered text live outside the E2E stack and only a reload takes the whole heap. That reload is the SAME replacement `page_lifecycle_web.dart` already performs on every thaw of a frozen PWA, so it lands on this app's best-tested boot — which then demands the code, since a wrapped device boots locked whatever the auto-lock window says.
- **Revocation is contract-preserving, and that is what keeps it safe.** A revoked store is never destructive and never answers "absent": sealed sig reads throw `SigStoreUnreadable('revoked')` (a null identity read is what mints a new identity), sealed content rows are served AS THEIR RAW ENVELOPE so `recordExists` still answers TRUE and nothing is retired as lost, `readAll` stays presence-preserving so `_hasPriorInstallResidue` still sees the rows, and sealed WRITES are refused rather than sealing under a dropped key. `EncryptionProvider.revokeForPasscodeLock` clears `isE2EReady` BEFORE the teardown, so no decrypt can run against a revoked store — that is what stops a permanent `[Decryption failed]` being persisted over a readable row. `restoreAfterPasscodeUnlock` re-initialises E2E on an unlock the process survived (native, or a reload the platform refused), and the revoker SERIALIZES revoke/restore so an immediate unlock cannot overtake the teardown.
- **Android keeps the UI-barrier shape on purpose**: with wrapping off the same keys are readable again the instant the store re-opens, so a teardown would cost an E2E re-init and buy nothing. `_lock()` therefore checks `_wrapKeys && await _vault.isWrappingOn()` before revoking anything — a passcode whose wrap enable failed also does not revoke.
- **4-digit is refused wherever wrapping is on** (`_modeAllowed`): 10 000 candidates are minutes OFFLINE once the code is the key (the published Bitwarden PIN exploit). It stays available while the passcode is only a gate.
- **The mode refusal alone was not the control it looked like** (review finding, fixed 2026-09-05). `_modeAllowed` refuses the `digits4` ENUM; the *alphanumeric* mode validated LENGTH ONLY, so `1234` typed as a Custom code produced exactly the 10^4 KEK space the refusal exists to forbid — and `123456` the same 10^6 space as `digits6`. `refusePasscode(code, mode, keyMaterial: _wrapKeys)` now enforces `kPasscodeMinKeyMaterialLength` (6) **and at least one non-digit** on the custom path, and it returns a REASON (`PasscodeRefusal.tooWeakForKeys`) rather than a bare false, because the setup screen has to name the rule the user hit — a silent refusal there surfaced as "this device could not secure the passcode", which points at the destructive erase. The 4-digit row is also gone from the options sheet under wrapping (`PasscodeSetupScreen.keyMaterial`): a choice that can only fail is a trap. Owner ruling 2026-09-05; `digits6` deliberately stays, so the same 10^6 space is still reachable by keypad — the floor buys the *shape* rule, not strength.
- **Every credential check is on ONE throttle ladder** (review finding, fixed 2026-09-05). `unlock` consulted `lockoutRemaining` and counted failures; `verifyCurrent` — the Settings prompt behind Change and Turn-off — called `_matches` directly, so it was an unmetered oracle: anyone reaching a momentarily-unlocked app could grind the code at KDF speed, leave no persisted trace, and on web recover the KEK and hence every future lock. `verifyCurrent` now refuses while the cooldown runs (before the KDF, so a correct code is not confirmed either), clears the ladder on success and advances it on a wrong code via the shared `_clearAttemptState`/`_registerFailedAttempt` helpers `unlock` also uses; `change` and `disable` gate on `verifyCurrent` instead of `_matches`. Still soft, and honestly so: the counter and the deadline are cleartext prefs and `lockoutRemaining` compares against the WALL clock, so a forward clock jump clears a cooldown — it stops hand-typed guessing, never an offline attack.
- **Android is deliberately excluded** (`wrapKeys` defaults to `kIsWeb`): the same material is already Keystore-backed behind `FLAG_SECURE`, so wrapping there would convert every Keystore fault into permanent history loss on the platform where a forgotten code is survivable. `ContentKeyWrap.instance` also has NO meta store off-web — otherwise every "is wrapping on?" call in a widget test hangs on a platform channel that never answers (that is exactly how two screen tests failed first).
- **The mint now records a durable `IDENTITY_MINTED`.** It previously left only a `debugPrint`, so a misclassification was inferable in the field only from the peer identity-change cascade hours later. Also new: `PASSCODE_WRAP_ENABLED` / `PASSCODE_WRAP_ENABLE_FAILED` / `CONTENT_STORE_LOCKED`.
- **Live-verified 2026-09-04 on web:** enabling a 6-digit code wrote the meta record and wrapped both key families; a reload with a FRESH `passcode_last_active_at` still demanded the code; while locked the durable log showed zero `IDENTITY_MINTED`, zero `SIG_STORE_FALLBACK` and 26 sealed `sig_e2e_*` rows untouched; the right code brought the app up with no identity-incomplete banner.
- **The re-lock was live-verified by killing the heap, not by reading code (2026-09-04).** With the app unlocked, a JS marker was planted (`window.__relockProbe = 'alive'`), the header padlock tapped, and the marker came back **undefined** — the document really was replaced. The fresh boot showed "Wpisz kod", `fp_passcode_kek_meta_v1` was still present, the 26 sealed `sig_e2e_*` rows were untouched, the durable log held **zero** `IDENTITY_MINTED` and **zero** `SIG_STORE_FALLBACK`, and the right code brought the app back up. On Android the same padlock locks and unlocks with E2E still up, and never creates a meta record.

### 10b. Phase 1 — the gate and its recovery model

- **On ANDROID it is a GATE, not at-rest encryption, and that is an owner decision (2026-09-03), not an oversight** — on web §10a now makes the code real key material. `PasscodeProvider` stores a PBKDF2-HMAC-SHA256 verifier (600k iters, `services/passcode_kdf.dart`); the verifier alone wraps nothing, and on Android nothing else is wrapped either, because `services/encryption/content_key_manager.dart` documents auth-bound key material as a new way to LOSE history. Honest reach without wrapping: Android's guarded material is Keystore-backed behind `FLAG_SECURE`, so the gate is a real improvement; **on web the verifier sits in the same localStorage as everything it guards** (`signal_stores.dart:30-52`), which is exactly why wrapping exists there. Never claim more in UI copy — `passcodeScopeNote` says exactly this.
- **There is NO password door: forgetting the passcode costs the DEVICE'S DATA (owner ruling 2026-09-04, replacing the 09-03 logout model).** A recovery path the account password can walk through is not a lock, and no key-derived lock in the field ships one (Telegram: *"if you forget your passcode, you'll need to reinstall the app"*; Threema: *"there is no way to recover lost PIN codes"*; Phantom: "Forgot password → Reset & wipe app"). The lock screen's only escape is `services/local_data_eraser.dart` behind a **typed confirmation** (`passcodeEraseConfirmWord`, ASCII in every locale — `ERASE`/`USUN` — because a diacritic is untypeable without the right IME, and this screen is all the user has). `PasscodeGate._erase` runs the eraser, re-runs `PasscodeProvider.initialize()` so the gate opens on the now-empty store, then `AuthProvider.logout()`. `clearForRecovery()` is GONE — the provider exposes no way to drop the credential without destroying what it guards.
- **The eraser's arm ORDER is load-bearing, and each arm is isolated.** Preferences (which hold `passcode_enabled`) go FIRST: a keystore that refuses after the flag survives is the `credentialDamaged` shape, i.e. a lock screen no code can open. Arms: prefs → secure storage (`readAll` + `delete` per key, Android only) → `DriftRecordDb.deleteDatabaseFiles()` (native) → `utils/origin_storage_wipe.dart` (web: localStorage + sessionStorage + every IndexedDB + every CacheStorage; the service-worker registration is left alone so an offline user can still load the app after the reload). A partial erase is REPORTED (`LocalDataEraseReport.failed` → `passcode-erase-partial`), never silently claimed as a clean slate. It finishes with `E2ePersistentDiag.clear()` **before** recording `LOCAL_DATA_ERASED`, or the in-RAM diag ring re-persists the pre-erase message/peer ids the user just destroyed (found in live QA).
- **"Just uninstall the PWA" is not a reset and must never be the advice.** web.dev: *"Deleting the icon may not clear the storage that a PWA is using"*, and the W3C declined a manifest uninstall event — a reinstalled PWA can come back with the old `localStorage`, including `flutter.passcode_enabled`. Only an Android uninstall genuinely clears app data. That asymmetry is why the erase is in-app.
- **Scope copy is per-platform and each half must match what that platform actually does** (`passcodeScopeNote(l10n)` in `screens/passcode_unlock_screen.dart`): Android says the lock covers this device and the code never reaches the server (`passcodeScopeNoteDevice`; the keystore-held verifier and `FLAG_SECURE` are its REASON, not its wording); **web says the code encrypts this browser's keys** (`passcodeScopeNoteBrowser`), so a copy of the profile is useless without it — which is the §10a guarantee, not a hedge. ⚠️ Until 2026-09-05 the web half still read *"It does not encrypt stored data: someone with access to this browser profile can bypass it"* — true in Phase 1, FALSE once wrapping shipped, and false in the harmful direction: a user told the lock is cosmetic has no reason to choose a strong code at the exact moment the code became the only barrier. When §10a's reach changes, this string changes with it. What we still do NOT claim: the passcode's strength is the passcode's entropy, and the wrapped envelopes plus the KEK salt live in the same origin storage they protect, so a short code falls to an OFFLINE attack — hence the `kPasscodeMinKeyMaterialLength` floor (6 chars, not digits-only) that `refusePasscode(..., keyMaterial: true)` enforces on the custom path and `_modeAllowed` enforces by refusing `digits4`. Bitwarden ships the same candor about its PIN ("can weaken the level of encryption"). Comparative research with sources: `.planning/passcode-lock/comparison-and-solution.md`.
- **The gate lives in `MaterialApp.builder`, above the Navigator, and hides the app with `Offstage` — never by unmounting.** Unmounting `MainShell` would drop the socket, the active conversation and in-flight sends. `Offstage` skips paint, hit-test AND semantics (verified live: the chat list disappears from the a11y tree while locked). Consequence: the lock screen has NO Navigator above it, so its confirm steps are INLINE — `showDialog` there throws.
- **The storage-loss notice (`_StorageLossLayer`, metadata-privacy PR2.3) is a sibling layer in that same `Stack`: above the app, below the lock, Offstage under the same `covered` flag — and it YIELDS to the device-link gate (2026-09-22).** Because the builder wrapper sits above the whole Navigator, the notice would otherwise paint over `AuthGate`'s gate: a Keystore-only loss kills the SQLCipher key and the Signal identity together, so the boot latches the loss and opens the gate in the same second, and the file-only notice hid the gate's phrase door (driven on a Pixel 7, Run C′). The layer returns nothing while `needsDeviceLink || identityCheckUnavailable`; the latch is process-scoped, so the notice appears the moment the gate releases (`test/widgets/storage_loss_layer_test.dart`).
- **`PasscodeLockState.unknown` counts as locked.** Painting the shell for one frame on a locked cold start defeats the feature.
- **The boot read is bounded, and it now has THREE verdicts, not two.** `initialize()` reads the enabled FLAG first via `PasscodeStore.readEnabledFlag()` (prefs only, cheap) and then wraps `store.load()` in `kPasscodeStoreReadTimeout` (6 s, derived — see the next bullet), because a store that HANGS is real (`SharedPreferences.getInstance()` never answers under the widget-test binding without mock values) and holding `unknown` forever bricks the app behind a blank surface. The verdicts: (a) **nothing readable, not even the flag** ⇒ treat as NO passcode (`PASSCODE_STORE_UNREADABLE`), because inventing a lock for a user who may never have set one would let a storage hiccup lock them out; (b) **flag TRUE and the read ANSWERED that the secret is gone** ⇒ `credentialDamaged`, gate fails **CLOSED**, terminal, erase is the way out (`PASSCODE_CREDENTIAL_DAMAGED`, every entry answers `unavailable` not `wrong`); (c) **flag TRUE and the read never ANSWERED** ⇒ `credentialUnavailable`, gate fails closed but **retryable** — the provider re-reads with backoff (400 ms → 8 s, capped, cancelled in `dispose`) until storage answers, and `credentialResolved` shows `passcodeCredentialLoading` with the keypad disabled instead of an error.
- **(c) exists because conflating it with (b) was a data-destroying lockout, found on a device (2026-09-04).** With a 250 ms per-attempt budget, EVERY cold boot of the debug build on a loaded Pixel emulator lost all three attempts, so a device with a perfectly intact credential reported `PASSCODE_CREDENTIAL_DAMAGED`, refused the correct 4-digit code with *"Nie udało się zabezpieczyć kodu na tym urządzeniu"*, and offered only the destructive erase. A first Keystore read after process start unwraps a key and is simply not a 250 ms operation. Now: **1.5 s per attempt**, `_readSecrets` retries the whole triple (100 ms / 200 ms delays, same reasoning as `AuthTokenStore.read`) and reports `readFailed` distinctly from "absent". After the fix the same emulator cold-boots with no `PASSCODE_SECRET_UNREADABLE` at all and the code works.
- **Reading the flag separately is also what closes a full BYPASS.** The flag used to come out of the timed `load()`, so a load that overran the ceiling was indistinguishable from "no passcode was ever set" — and that branch UNLOCKS the app. A slow Keystore was therefore a way in. **The budgets stay ordered and a test asserts it:** `DevicePasscodeStore.secretReadBudget` (4.8 s worst case) < `kPasscodeStoreReadTimeout` (6 s), so a slow-but-working store resolves through the store's own retries rather than through the ceiling; but even if the ceiling fires, a flagged device answers LOCKED.
- **Any test that mounts `FireplaceApp`, `SettingsScreen` or `ConversationsScreen` now needs a `PasscodeProvider`** (use `test/support/passcode_fakes.dart`) **or `SharedPreferences.setMockInitialValues({})`** — otherwise `ProviderNotFoundException`, or a pending-timer failure from the bounded read.
- **Auto-lock is a persisted timestamp, never RAM state.** `noteBackgrounded()` stamps `passcode_last_active_at` on the way out (both `didChangeAppLifecycleState` and the web `registerTabVisibilityListener`); a cold boot applies the SAME `shouldLockOnForeground` policy as a foreground return, because on web a frozen PWA is REPLACED by a hard reload (§4) so "cold boot" and "came back" are one event. Choices are `[0, 60, 300, 3600]` s, default 60. Fail-closed on a missing stamp or a backwards clock.
- Brute-force resistance is soft by construction: 5 free attempts then 30 s/1 m/5 m/15 m/1 h (`passcodeBackoffFor`, NIST SP 800-63B-4 §3.2.2's own "30 seconds up to an hour" curve), counter in the same storage as the verifier. It stops hand-typed guessing, not offline attack. `passcodeAttemptsRemaining` drives a "N attempts left" subtitle at ≤2 left. **Deliberately NOT a wipe-at-N** (Phantom deletes its local encrypted backup after 7 wrong tries, Ledger factory-resets after 3): those systems restore from a seed phrase, this app's local history has no backup, so an attempt-triggered wipe would hand a data-destruction button to whoever picks the phone up.
- Entry points: Chats header padlock (`conversations-passcode-button`, left of `+` — enabled → `lockNow()`, not configured → setup) and Settings → SECURITY (`settings-passcode-row`). Numeric modes draw the app's own hex keypad (no IME on the lock screen); the custom alphanumeric mode uses a real field with an explicit submit.
- **Verified on both platforms 2026-09-04, not just in tests.** Web (dev server + browser tool): 3 wrong codes → "Zostały 2 próby przed przerwą", right code unlocks, erase panel refuses until the word is typed, then 66 localStorage keys (35 `sig_*`) → 1, both IndexedDB databases and the `fp-boot-marker` cache gone, app back at the login screen. Android emulator (API 34, debug, real Keystore): setup → `FlutterSecureStorage.xml` holds `fp_passcode_{salt,verifier,iterations}_v1` while prefs hold only flag+mode; lock/unlock through the real BoringSSL PBKDF2; erase took prefs 6→1 keys, secure storage **61→0**, `files/fp_content.db{,-wal,-shm}` 3→0; re-login then works and the app shows its existing "no encryption keys on this device" notice, i.e. the identity re-mint the warning copy promises. Two defects were caught only by that pass: a dead confirm button (the web IME path updates the controller without firing `onChanged`, so the field is bound with a controller LISTENER, never `onChanged`) and the diag-ring resurrection above.
- **Re-verified on Android after Phase 2 (2026-09-04, second pass).** Fresh install → login → identity mint → 4-digit passcode (accepted, as `_modeAllowed` allows it with wrapping off): prefs held only `passcode_enabled` + `passcode_mode`, `FlutterSecureStorage.xml` held `fp_passcode_{salt,verifier,iterations}_v1`, **no** `fp_passcode_kek_meta_v1` and **zero** `fpwk1:` envelopes anywhere (wrapping stays off by construction). Cold boot → lock screen → correct code unlocks, with no `PASSCODE_SECRET_UNREADABLE` after the budget fix. Mid-session padlock → lock → unlock leaves E2E up (nothing is revoked off-web). Erase with the typed `USUN`: prefs 5 → 1 (only the diag ring, re-created by `LOCAL_DATA_ERASED`), secure storage **33 → 0**, `files/fp_content.db{,-wal,-shm}` **3 → 0**, back at the login screen. Shots in `.planning/passcode-lock/shots/relock-android-*.png`.
