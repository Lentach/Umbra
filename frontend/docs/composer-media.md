## Composer, media, and platform gotchas

- Chat composer viewport: non-embedded chat uses `ChatComposerViewport`; `Scaffold(resizeToAvoidBottomInset:false)`, list bottom padding = composer height + keyboard inset, composer `Positioned(bottom: keyboardInset)`.
- **Composer ergonomic bottom buffer = RESTING clearance; focus must never collapse it (owner report 2026-09-12, reverts H1 from 0.0.99).** `bottomInteractivePadding` (`chat_input_bar.dart`) pads the bar over the home indicator and — inside `MainShell`'s `extendBody: true` Scaffold, where the bottom nav height arrives as `MediaQuery.padding.bottom` — over the bottom nav; it also sizes `ChatActionTiles.bottomPadding`. Its `keyboardVisible` predicate is `viewInsets.bottom > 0 || sharedInset > 0` and nothing else: a real inset simultaneously lifts the composer (`ChatComposerViewport`'s `Positioned(bottom: effectiveInset)`), so collapsing then is invisible. Folding `_focusNode.hasFocus` in (H1, to avoid resizing an open action panel mid-keyboard-animation) moved the bar DOWN by the whole clearance on every tap with nothing lifting it — 72 px in the probe geometry, burying the input row behind the nav on desktop web where no soft keyboard ever arrives, and dropping it to the physical bottom edge on phones before the inset ticks up. Regression: `test/widgets/input/chat_input_bar_send_test.dart` "composer focus leaves the bar geometry untouched" (bar height) + "a raised web keyboard inset removes the ergonomic bottom buffer".
- Composer emoji button/panel: RESTORED 2026-07-28 by owner ruling (it was removed in 0.0.115 as a "keyboard duplicate", but the premise was wrong — not every soft keyboard exposes an emoji key). The toggle (`composer-emoji-toggle` key) opens `FireplaceEmojiPicker` as a composer bottom panel that REPLACES the keyboard: `_setEmojiPickerVisible` is the single visibility mutation point keeping `composerBottomPanelPinned` (composer_keyboard_signals.dart) in sync (the exit-slide completion and `dispose` also release the pin), and `ChatComposerViewport` anchors at `bottom: 0` while pinned so the panel occupies the keyboard's space from the first frame. Keyboard and panel are mutually exclusive (focus gain closes the panel); recording start and chat-surface taps close it; system back closes it via `PopScope`; sending from the panel keeps it open (Telegram parity). Panel LAYOUT is instant — the 320px block is there from the first frame and never animates height (no SizeTransition); only the CONTENT slides via `SlideTransition` under a `ClipRect`, on open and on keyboard-neutral closes (chat-surface tap, tap outside, system back), while keyboard-replacement closes (focus gain, toggle back) and recording start unmount instantly.
- Composer send key (owner ruling 2026-07-28): on mobile (Android/iOS by `defaultTargetPlatform`, native AND phone PWA) the IME action key is `TextInputAction.newline` — the action key inserts a newline and only the on-screen send button sends. Desktop (web/native) keeps `TextInputAction.send` + `onSubmitted` + Ctrl/Cmd+Enter. Do not "unify" these.
- iOS WebKit keyboard inset comes from `visualViewport` via `web_keyboard_inset.dart`; Flutter `MediaQuery.viewInsets.bottom` is unreliable there.
- Composer collapse guard defers inset collapse only for send/edit/staged/video-send/action-toggle/ping-refocus operations (`_armComposerCollapseGuard`, 600 ms auto-clear); genuine keyboard dismiss should collapse immediately.
- Composer tap-outside: `ChatInputBar` groups the text field + composer controls in one `TapRegion`; taps outside the whole composer unfocus on Android/desktop web, while iOS WebKit skips the unfocus in BOTH outside callbacks (`_handleComposerTapOutside`, shared by the region and the bare text field) to avoid the send-button keyboard bounce — an iOS outside tap still closes open composer panels.
- Composer action panel is part of the outer composer `TapRegion`; taps inside controls must not blur the field. The lower action panel mounts/unmounts INSTANTLY (no `SizeTransition` — a 250ms animation relayouts a ~300px block through the exact keyboard show/hide window: iOS counter-pan flash, Android stale-composited-region void). Taps on the chat surface call `ChatInputBarState.dismissForChatSurfaceTap()`: they unfocus the keyboard on ALL platforms even when the lower action panel is open (2026-07-07 Android ruling, extended to iOS 2026-07-09: the iOS keep-focus gate made the tap's DOM blur fight the still-focused framework node — keyboard closed then bounced back); only the panel itself survives the tap. Ping is keyboard-neutral: the ping tile sits in a `FocusGuardArea` (iOS) and `ChatActionTiles.onPingSent` drives a non-iOS post-frame refocus gated on focus-at-pointer-down. Do not put only the `TextField` in the tap region, and do not rely only on `TextField.onTapOutside` because the message list owns gestures.
- DOM focus guard (`web_focus_guard.dart` + `FocusGuardArea`) prevents canvas-painted composer controls from stealing focus when input is already focused. It does not replace `onTapOutside`. **Device-proven LOAD-BEARING (2026-07-07 probe): with the guard disabled, every send-button tap dismissed the keyboard — the 0.0.64 `onTapOutside` fix does not stop the DOM-level blur. Never remove it.** `FocusGuardArea` re-measures its rect per shared-inset event (not only on build): the composer MOVES during the iOS keyboard pan without its subtree rebuilding, and stale rects = the guard misses = every first tap after a keyboard rise blurs. The `_sendJustFired` iOS fast-refocus machinery was probe-proven unobservable and deleted; the non-iOS post-frame refocus fallbacks in `_send`/`_sendStaged` stay (the guard is iOS-only). The flash-fix predicted-inset pre-arm is deleted FOR GOOD (2026-07-09): the panel flash died from the H1/H2/H3 transition fixes alone, device-confirmed on 0.0.99 — do not reintroduce without new device evidence.
- Trailing composer control is one always-mounted 48x48 stack: mic idle, text-send for draft/staged image, voice-send while recording, spinner while sending. Do not swap Row siblings; unmounting dismisses keyboard.
- Text-send glyph is `HexSendButton` (`widgets/input/hex_send_button.dart`): the app's pointy-top hexagon (`hexPath`/`kHexWidthRatio`, shared with the Chats avatars and the Contacts honeycomb) under an ember gradient derived from `colorScheme.primary`. **PAINT ONLY** — no gesture recognizer, no semantics; `_ComposerTapSendOverlay` above it still owns the full 48x48 hit region, tooltip and semantics, because an `IconButton` there wins the gesture arena and blocks hold-to-record. **The glyph color MUST come from `RpgTheme.readableOn(accent)`, never `Colors.white`** — the circular predecessor hardcoded white and landed at 1.56:1 on `cosmic` (#8FD8FF, effectively invisible), 2.57:1 on `blue`, 3.02:1 on `dark`, all under the 3:1 non-text gate. Regression: `test/widgets/input/hex_send_button_test.dart`. The voice-send layer is deliberately still a bare accent `Icons.send_rounded` with no disc.
- **Video messages (Telegram model since `feat/video-nits`, 2026-09-05).** The bubble (`widgets/message/video_message_content.dart`) autoplays MUTED and looping in place when `SettingsProvider.autoplayVideos` is on (default true, prefs key `autoplay_videos`, Settings → Preferences row `settings-autoplay-videos-row`), the row has `mediaUrl` + `mediaKey` + `mediaIv`, and ≥60% of it is on screen (release below 30% — hysteresis). **Exactly ONE inline session lives at a time** (`inline_video_arbiter.dart`, newest MESSAGE wins — see the slot-policy bullet below — loser disposes) because media is whole-file AES-GCM: every live session is a decrypted blob of up to 20 MB in RAM. The only inline control is the speaker toggle (`video_inline_mute_toggle`); a tap opens `showVideoFullscreen(startAt:)`, which plays WITH sound and returns the last position so the bubble resumes there. `didUpdateWidget` re-evaluates when the decrypt pass fills in the keys — a history row carries the plaintext `mediaUrl` column long before its key, and nothing scrolls in between. The fullscreen seek bar sits 64 px above the bottom edge: at 12 px it was inside Android's gesture-navigation zone and scrub drags fired swipe-up-home.
- **Gestures over a `<video>` on the web (2026-09-06, emulator-reproduced):** `video_player_web` mounts the element as an `HtmlElementView`, and the engine does NOT deliver pointer events whose DOM target sits inside a platform view — a `GestureDetector` wrapping `VideoPlayer` is dead on a real touch (the poster works, the playing clip does not). Fix is `pointer_interceptor`, **with the handler as the interceptor's CHILD**: the interceptor's own render box is a platform view too, and its recognizer wins the arena sweep over any ancestor detector (verified: sibling interceptor + ancestor detector = touch hits `DIV[flt-platform-view]`, nothing fires). Both the bubble and the fullscreen stage (`_stageGestures`) are wired this way. **Fullscreen contract:** `showVideoFullscreen` returns the position reported from `PopScope.onPopInvokedWithResult` — NOT `dispose`, which runs after `showDialog` has already resolved (that bug made every return resume from the handoff). Chrome is Telegram's: back chevron top-left, sender/day header pill, `elapsed — slider — remaining`, swipe-down dismiss (22 % of height or a fling), loop at end. Inline: `0:12 🔇` pill top-left toggles mute FOR ONE PLAYTHROUGH — the loop wrap (a backward position jump; inline has no seek bar) and every new inline session re-mute, while fullscreen keeps sound; bottom corners belong to the bubble's time/ticks.
- **Inline slot policy is NEWEST-VISIBLE-WINS, not latest-requester (2026-09-06):** `InlineVideoArbiter.request(owner, onRevoke, priority: createdAt.ms)` returns `bool` — a higher priority revokes the holder, a lower one is DENIED and the bubble sets `_deniedByNewer` so the arbiter's next release re-evaluates it (post-frame, never inside the notifier's dispatch). Only a denied bubble reacts to arbiter traffic: a bubble whose own load failed must not re-request on its own release or it retries every frame and hammers the server (that loop is what the first cut did; the widget test pins both halves). Owner report that motivated it: on chat open the second-to-last clip played while the last sat blurred — mount order decided.
- **Media blob downloads are throttled SERVER-SIDE and the client must never treat them as free:** `GET /media/msgs/*` (every image AND video) is 600/min per client IP with `Cache-Control: private, max-age=1y, immutable`. It was 60/min with no cache header, and inline autoplay (each scroll-in, fullscreen open, fullscreen close and the sender's post-ack refresh is a full re-download) tripped 429 in one session on the owner's phones — "plays once, then broken", "reopen → plays once → broken". Symptom in the durable log: `VIDEO_LOAD_FAILED stage=fetch_decrypt … 429`. Repeat loads now come from the browser cache; anything that adds a fetch per interaction still has to fit that budget.
- **Fullscreen swipe-down is animated:** after release the stage keeps travelling (`_slide` AnimationController, easeIn off the bottom in 80–220 ms scaled by fling speed, easeOutCubic snap-back in 220 ms); `MediaQuery.disableAnimationsOf` collapses both to a snap. `_dismissing` latches so a second drag cannot fight the exit; the pop happens only once the stage is off-screen, so the dialog's own fade is invisible.
- **Stills and GIFs share that swipe-down since 2026-09-14 (owner report: it worked on video and did nothing on a photo).** `widgets/media/swipe_down_to_dismiss.dart` holds the gesture + physics and `widgets/media/fullscreen_image_viewer.dart` is the stage used by `image_message_content.dart` and BOTH gif paths (network blob + memory bytes). **`video_fullscreen_view.dart` deliberately keeps its own copy** — its drag is entangled with chrome hiding, playback state and the `pointer_interceptor` over the platform `<video>` — so the constants live in two places: change one, change the other. The load-bearing detail for stills is the zoom hand-off: `InteractiveViewer` claims the vertical drag whenever panning is enabled, so `panEnabled` is true ONLY while zoomed in and the dismiss drag is armed only at rest scale — two recognizers must never contend for it. And the controller is built in `initState`, never as a lazy `late final`: a viewer opened, zoomed and closed without a single drag would otherwise first touch it in `dispose`, where `createTicker` trips "Looking up a deactivated widget's ancestor is unsafe" (the zoom test caught exactly that).
  One presentation change rode along and is DELIBERATE, not a slip: the GIF dialogs now pass `insetPadding: EdgeInsets.zero` like the image one, so GIF fullscreen is edge-to-edge. The shared stage paints the fading black backdrop the drag needs (the barrier cannot, because it must thin out under the finger), and inside a Dialog's default margins that backdrop renders as a black rounded box. Edge-to-edge is the only coherent option once the gesture exists — flagged to the owner 2026-09-14 under the "explicit OK" rule.
- **Video geometry (`mediaWidth/Height/ThumbHash`) rides in the E2E envelope and has TWO known ways to go missing, both fixed the same day:** (1) the web probe (`utils/video_probe_web.dart`) read `videoWidth/Height` at `loadedmetadata`, where WebKit still reports 0 for some QuickTime camera recordings — it now waits ≤3 s for `resize`/`loadeddata`, and the blob is labelled by extension (`videoMimeForFilename`, `.mov` → `video/quicktime`); (2) the video RETRY branch of `retryFailedMessage` rebuilt the pending payload without geometry, so a clip that failed once reached the peer as a 220 px legacy square with a blank poster while the sender's optimistic bubble looked right (regression in `messaging_provider_media_send_test.dart`). Messages already sent without geometry stay square — nothing re-probes on the receiver.
- Android web attachment sheet has FOUR doors: Galeria (`image/*,video/*`), Aparat (`image/*` + `capture`), **Nagraj wideo** (`video/*` + `capture`, key `attachment-door-record-video`), Plik. Android has no single input that offers photo-or-video — `image/*`+capture opens the still camera and `video/*`+capture the camcorder — while iOS ignores `capture` and shows its own "Take Photo or Video" sheet, which is why iOS could record a video from the paperclip and Android could not.
- **The action row's `delete_forever` tile is the only DESTRUCTIVE control in the composer, and its hold is an accident guard, NOT consent (2026-09-14).** `_LongPressActionTile` holds for 1500 ms under a centre progress ring and aborts on release — but it fires `clearChatHistory`, which makes the server run `deleteAllByConversation`: every row of the conversation dropped for **BOTH** participants, all media unlinked, irreversible, pre-link (`historia sprzed połączenia`) history included. So the tile now carries a `tooltip` like every sibling `_ActionTile` (an unlabelled destructive tile told the user nothing), the ring's caption is a `holdLabel` stating the scope while releasing still cancels — it used to read `clearingChat` ("Czyszczenie…"), present tense for a wipe that had not been requested yet — and completing the hold opens `widgets/dialogs/clear_chat_dialog.dart` (same shape as `message_delete_dialog.dart`: `GlassDialog`, destructive label in `colorScheme.error`, cancel from `MaterialLocalizations`). **A 1.5 s hold cannot be read and weighed; do not "simplify" by wiring the gesture straight back to the emit.** The gate is pinned by `test/widgets/dialogs/clear_chat_dialog_test.dart` (confirm fires once, cancel and barrier-dismiss never fire).
- Voice recording is tap-to-toggle, not hold/lock/swipe. 500 ms minimum, 120 s auto-send. Recording waveform is decorative, not real amplitude.
- Ping and web voice playback use Web Audio (`ping_sound_web.dart`, `voice_player_web.dart`) to avoid iOS MediaSession cards.
- Web voice codec limit remains: Safari can decode AAC/MP4/MP3/WAV; WebM/Opus may not play on iOS.
- File/media helpers use conditional imports. Guard `dart:io`/`Platform` with `!kIsWeb`.
- `webcrypto` Android 16KB page-size patch: `patch_webcrypto_16k.ps1` edits the PUB CACHE (dropped by `pub cache repair`/SDK upgrade, PowerShell-only). `build-android.ps1` applies it best-effort; the HARD gate is the post-build ELF check `scripts/verify-apk-16k.mjs`. `flutter pub run webcrypto:setup` is for native test setup, not APK/AAB packaging.
- `MainActivity` package declaration must be `com.fireplace.app` even though the file path is still old.
- `kotlin.incremental=false` in `android/gradle.properties` is intentional mixed-drive cache damage control.
