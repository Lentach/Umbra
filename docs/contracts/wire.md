## Contracts

- E2E envelope: `{ content, messageType?, mediaUrl?, mediaDuration?, mediaKey?, mediaIv?, mediaWidth?, mediaHeight?, mediaThumbHash?, linkPreview?, senderListInfo?, msgId?, t?, ts?, to?, ttl?, re?, boxMedia?, tg?, e?, on?, auth?, k?, w?, rl?, ad?, u?, d?, since?, count?, av? }` (`k`…`count`: decisions 101–103, box section; `av`: decision 138, the profile photo reference of `{t: 'profile'}`, box section). Ciphertext format is `"{type}:{base64}"` (`3` PreKey, `2` Signal/whisper). The account server never receives an envelope: it rides inside the box blob only (box section).
  - `t` / `ts` (metadata-privacy PR3.1 slice (b), owner decision 13): `t` is the envelope type the box reader routes on — absent means a chat message (`'msg'`); a non-string `t` matches no type and is never read as a message. `ts` is the SENDER's send time in whole ms since the epoch (a box message has no server `createdAt`); anything but a positive int ≤ 8 640 000 000 000 000 (`DateTime`'s range) is absent. The receiver clamps it to its own receive time, so a peer can backdate but never future-date a message.
  - `msgId` is the message's WIRE id (metadata-privacy PR2.1): the sender's send token for that send, minted once per tempId and reused by every retry. It rides inside the plaintext, so it is how every receiving device (peer and own sibling) learns it. The receiver keeps it only if it matches the sender's minting shape `^[A-Za-z0-9_-]{8,64}$`, else drops the field, never the message. An edit envelope carries none. The client takes a wire id only from the decrypted envelope; an own row takes the token THIS device minted (the in-memory tempId map), never a server field. Persisted as the `_wid` stamp on the `_decrypted_` record beside `_wsid`, the sender's account id (written as a pair, first write wins); `EncryptionService.wireIdIndex()` maps `(senderId, wireId)` back to the local id. The key is sender-scoped because a wire id is unique only per sender and a peer sees ours in plaintext: a replay of one of ours sits under the peer's name and never shadows our copy, even when it lands first. The sender is only ever authenticated — the account whose pairwise session decrypted the envelope, or our own for our own sends. A `_wid` without `_wsid` claims nothing, and one sender's wire id held by more than one record maps to nothing. The box reader (PR3.1 slice (b)) dedups against the same stamps through `wireHeldByOther`, where ANY other record holding the pair counts — it asks "is it here", not "which row".
  - `to` (metadata-privacy PR3.1 sibling queues part B, E5): the PEER's user id on a SENT COPY — the envelope a sender's box send also encrypts for each of its own live siblings, identical to the peer's (same `msgId`, `ts`, content) plus `to`. It rides inside the E2E plaintext, so the box sees no account. Kept only as an int in 1..2³¹−1; a copy without it, or naming the reader's own account, is finished unshown. The peer's envelope never carries it. The copy is the longest envelope, so a link preview that would push IT past the frame is dropped from both (`boxEnvelope`), and the decision-18 fit proof (`box_frame_test.dart`) is measured on it.
  - `senderListInfo` is `{ ownVersion?, ownListHash?, peerVersion?, peerListHash? }` — the sender's view of BOTH parties' device-list versions, hashed as SHA-256 (base64) over the DAK-signed `listCanonical` bytes exactly as transported (multi-device spec §5.2 layer 2, §12 amendments (xv)/(xvi)). It rides inside the plaintext, so the server never sees, stores or validates it, and it is attached to every message. A party the sender holds no verified list for is ABSENT from the object, never reported as version 0. On receive it is untrusted peer data: a bare claim NEVER alarms and never changes trust (I7); a claim newer than the recipient knows buys at most ONE rate-limited device-list re-fetch and is then discarded; a claim older than the recipient's own verified version (or the same version with different canonical bytes) is a split-view signal, recorded durably for the operator; skew about the recipient's OWN devices renders only the calm "syncing devices" note, never the identity-changed surface. Unknown envelope keys are ignored by `E2eEnvelope.parse`, so an older peer omitting the field is normal.
- Socket readiness clock: after socket auth completes, server emits `socketReady` with `{ serverTime: string, deviceId: number }`; `serverTime` is an ISO-8601 UTC instant stamped at that completion. `deviceId` is which device of the account this socket is (multi-device spec §5.3) — the client cannot derive it, and it is load-bearing twice over: a send must exclude its own origin device (a device never seals a copy to itself), and the self-sync receive law only scopes an own row's origin once this value is CONFIRMED rather than the §8 default of 1 (spec §12 amendment (xii)).
  - Why: this is the client's only trustworthy clock reference for gating destruction of expired message plaintext. Destruction requires a fresh observation (never extrapolated past 30 minutes) and `expiresAt` plus a 5-minute grace.
  - Missing, stale, or unparseable `serverTime` fails silently closed: the client holds and never destroys expired plaintext — no error or log, while plaintext accumulates. This deliberate asymmetry accepts over-retention rather than permanent data loss: the local plaintext is the only readable copy, because the Signal ratchet consumed the key.
  - Compatibility: older clients ignore the extra field; newer clients against older servers receive no usable clock and therefore never destroy plaintext on expiry.
  - In-session refresh: client emits `getServerTime` (no payload); server replies `serverTime` with `{ serverTime: string }`, same ISO-8601 UTC semantics. The client's sweep timer asks only when its last observation aged past the 30-minute extrapolation bound (floor-limited to one unanswered request per 5 minutes), so a connection that outlives the socketReady observation can still destroy expired plaintext instead of holding it until the next reconnect. An older server simply never answers and the client stays fail-closed.
  - **Resume probe (Phase 4 step 4, E114g).** `ensureReconnectIfNeeded` on a socket that claims to be connected emits `getServerTime` and arms a 6 s probe that forces a fresh connect unless `_serverResponseCounter` moved: the `serverTime` reply moves it. `serverTime` is answered by a handler that reads no table (throttled 60 / 15 min per user), so every resume has an answer to wait for.
- **A throttled WS request ANSWERS; it never goes silent (2026-08-22).** `WsThrottlerGuard` emits a refusal to the caller and THEN refuses the handler, so the limit keeps its teeth while the caller learns why. The answer rides the request's OWN response event with the stable code `rate_limited` plus `retryAfterMs` — `provisioningComplete` → `provisioningCompleted { success:false, error:'rate_limited', retryAfterMs }`, and likewise for `openProvisioning` (`provisioningOpened`), `provisioningHello` (`provisioningHelloAck`), `provisionDevice` (`provisionDeviceAck`), `cancelProvisioning` (`provisioningCancelled`), `revokeDevice` (`deviceRevocationCompleted`), `updateDeviceList` (`deviceListUpdated`), `setRequestQueue` (`requestQueueSet`) and `getOwnRequestQueues` (`ownRequestQueues`). Only handlers that ACTUALLY carry the guard belong in that table (`THROTTLE_ANSWERS`) — an entry for an unthrottled handler is unreachable code that misrepresents this contract, which is why `uploadKeyBundle` was removed from it. An UNMAPPED handler falls back to `error { message:'rate_limited', event, retryAfterMs }`. **Why in-contract rather than one new `rateLimited` event:** a second refusal convention would be one more thing every future handler must remember, and the client would need a map from that event to whichever optimistic state to unwind — whereas these payloads flow into the settle/revert paths the client ALREADY has. Before this, `ThrottlerGuard` threw, Nest emitted `exception`, and the client (60+ named listeners plus `error`, never `exception`) heard NOTHING — so a throttled link-ceremony stage left the link UI waiting forever. Adding a throttled handler that holds client state means adding it to `THROTTLE_ANSWERS`.
- Takeover alarm (Phase 0a, spec `docs/design/multi-device.md` §6.0): `uploadKeyBundle` that REPLACES the stored `identityPublicKey` writes a durable `identity_change_audit` row and emits `ownIdentityReplaced` `{ occurredAt }` to the account's OTHER sockets (uploader excluded). Nothing else goes out since step 5: no push and no `peerIdentityChanged` to peers (decisions 115, 116); a closed device reads `ownKeyBundleStatus.identityReplacedAt` at its next open. Same-identity re-uploads (the every-connect path) stay silent. The branch fires on legitimate reinstalls too — client copy must say "new device/browser sign-in", never "hacked".
- Registration lock (Phase 0b, spec §6.1; **OPT-IN since (lxxiii) 2026-09-05 — the refusal below applies only to an ENROLLED account (`KeyBundlesService.isEnrolled`, an `account_authorizations` row); an un-enrolled account replaces its identity on credentials alone, `authorizedBy: 'unlocked'`, with the same audit row + §6.0 alarm**): `uploadKeyBundle` that replaces the stored `identityPublicKey` is REFUSED unless the account has a completed reset ceremony, which the upload SPENDS. **An ENROLLED account does not get the signature path at all ((liv), `KeyBundlesService.authorizeIdentityChange`)**: the §5.1 link blob ships `ikPriv` to every linked device, so a compromised linked device could otherwise mint a new IK, sign the change with the old one, and take the account identity with no ceremony and no delay. `identitySignature` + `nonce` (XEdDSA by the previous identity key over `newIdentityPublicKey ‖ userId ‖ nonce`, verified server-side with `curve25519-js`) is therefore honoured ONLY for an un-enrolled account — where the lock is not armed anyway, so the proof buys nothing but the `authorizedBy: 'signature'` attribution. Refusal emits `keyBundleUploaded { success:false, error:'identity_locked' }` — nothing written, no audit row, no alarm. Nonces come from `getRegistrationLockNonce` → `registrationLockNonce { nonce }`: 32 CSPRNG bytes, TTL 5 min, bound to the issuing socket, consumed by ONE upload attempt. Same-identity re-uploads and first-ever uploads are unaffected. **No `frontend/lib` code mints an `identitySignature`** — the client requests a nonce only for the (lxxviii) `restoreSignature` (`EncryptionProvider._requestLockNonce` + `EncryptionService.signRestoreProof`) — and a device that lost its keys cannot sign with them anyway, so in the live app the only routes through the lock are spending a completed reset ceremony and the (lxxviii) restore proof. A signed rotation belongs to Phase 2 / §6.3.
- **§6.2 recovery REBIND (client half, 2026-08-22).** When a reset teardown re-homes an account, `keyBundleUploaded` additionally carries `{ deviceId, access_token, refresh_token }` bound to the NEWLY allocated device. **The client MUST adopt that session and reconnect BEFORE publishing any key material** — the same ack triggers the one-time-pre-key upload, so delivering it first files those keys under the device the teardown just REVOKED, leaving peers served a bundle with no one-time pre-key and the next reconnect refused by the §5.5 gate. `ConnectionProvider` adopts via `onSessionRebound` (wired to `AuthProvider.adoptProvisionedSession`, the same storage path as login and as the §5.1 provisioning rebind), reconnects with `immediate: true` to bypass the connect debounce, and only then delivers the ack. The server half shipped in T6; the client half was missing until T8's probe ran the ceremony end to end.
- Reset ceremony (Phase 0b, spec §6.2/§6.2.1): `resetIdentityRequest { recoveryPhrase? }` → `identityResetStatus { status: pending|existing|cooldown|invalid_phrase|locked|not_enrolled, deadlineAt?, shortened?, phraseTooNew }` (`not_enrolled` is the (lxxiii) opt-in lock: no `account_authorizations` row, so there is nothing for a ceremony to authorize; `phraseTooNew` says the phrase was CORRECT but younger than the 6 h age floor, so the ceremony runs the full delay — told only to the requester, never in the room-wide broadcast); a NEW ceremony also broadcasts `identityResetPending { deadlineAt, shortened, occurredAt }` to the whole user room — no push since step 5 (decision 115): a closed app reads `ownKeyBundleStatus.identityReset` at its next open, and until then the ceremony's waiting time is the only protection. `resetIdentityCancel` → `identityResetCancelResult { cancelled }`, and on a real cancel `identityResetCancelled { occurredAt }` room-wide. Delay is **6 h** (spec (lxxxii) clause 1, was 72 h until 2026-09-08), or 1 h when a valid recovery phrase at least 6 h old is presented — the phrase SHORTENS, never silences, and the shortcut is single-use. `setRecoveryKey { phrase, backup? }` → `recoveryKeySet { success }` (plus `recoveryKeyEnrolled { replaced, occurredAt }` to the whole user room, no push) stores an Argon2id verifier (19 MiB / t=2 / p=1) and, when `backup` is present, the phrase-sealed identity blob beside it ((lxxviii) clause 1, columns added by migration `0017`) — never the phrase itself. Tables `identity_reset_requests` (terminal states; a partial unique index enforces one pending per account) and `recovery_keys`, migration `0014`. A completed ceremony stays spendable for 24 h — an unused grant lapses, because `cancelReset` cannot reach a row that already left `pending`.
- **The recovery phrase alone resets the password (spec (lxxxii) clause 2, 2026-09-08, owner: "the seed is the account").** REST `POST /auth/recover { identifier, phrase, newPassword }`, unauthenticated, 5 / 15 min per IP; identifier resolves exactly like login (an unknown or ambiguous name pays a DUMMY Argon2id verify — no timing oracle); the phrase is verified against `recovery_keys.verifierHash` through the SAME failure counter + 1 h lockout the §6.2 shortcut uses, never spent, `usedAt` and the age rule ignored. Success = `revokeAllForUser` → bcrypt + `passwordChangedAt` → wait for the next whole second (a JWT `iat` in the stamp's second is rejected by `JwtStrategy`) → the ordinary login tokens for the live primary. Refusals: 401 `Invalid credentials` (unknown name / wrong phrase / none enrolled — one wording), 423 `recovery_locked`, 400 DTO. No push, no broadcast — other devices learn on their next refresh. Client: `AuthProvider.recoverPassword`, `AuthStatusCode.phraseRejected`.
- `checkOwnKeyBundle` → `ownKeyBundleStatus` now carries `{ exists, identityReset: {status, deadlineAt, shortened} | null, identityReplacedAt: string | null, identityReplacedTo: string | null, linkingEnabled, hasIdentityBackup, hasRecoveryPhrase }`. The extra fields are additive; a missing or malformed payload still means UNKNOWN and MUST NOT authorize key generation. **`hasIdentityBackup` (a phrase-sealed blob exists, (lxxviii)) and `hasRecoveryPhrase` (ANY `recovery_keys` row, (lxxxiii) clause 4) are different questions:** a phrase enrolled before 0.2.23 has a verifier and no blob — it still resets the password at `/auth/recover`, so the Chats nudge and the post-registration offer key off `hasRecoveryPhrase`; only the devices screen's enrolled-primary nudge keys off the blob. Prod 2026-09-09: 2 verifier-only rows, 0 blobs — the first cut (0.2.34) nagged exactly those two. `identityReplacedAt` is what lets a session that was offline during a replacement raise its banner at connect time, `identityReplacedTo` (the key that change ENDED at, (lxxx) clause 5) is what stops a wiped-then-RESTORED install — which has no dismissal watermark left — from alarming about its own history: a row ending at this device’s own published identity is not pending, while one ending at any other key still alarms, and `shortened` is what stops a session reconnecting INTO a 1 h recovery-key ceremony from describing it as the default 6 h one.
- Per-device key material (Phase 1, spec §4/§5.1/§8): `fetchPreKeyBundle` takes an OPTIONAL `deviceId` (integer 1..100) naming which device of the target to build a session with; absent means device 1, so a client that predates devices keeps working — the rollout order is server first, clients later. **Uploads do NOT take a device from the payload**: `uploadKeyBundle` and `uploadOneTimePreKeys` write to the device named by the caller's own JWT (`client.data.user.deviceId`, absent claim = 1), because a bundle belongs to the device whose authenticated session uploaded it — both DTOs still DECLARE an optional `deviceId`, and both handlers ignore it. Key bundles are unique per `(userId, deviceId)` and one-time pre-keys per `(userId, deviceId, keyId)`, so two devices may both hold keyId 0; the identity-epoch invariant is re-keyed to `(identityPublicKey, deviceId)` at all three sites (purge / claim / count). A device with no bundle of its own is served NOTHING — never a sibling's bundle, which would build a session it cannot decrypt. `keyBundleUploaded` gained `identityChanged: boolean` so the uploading device can tell its own replacement from someone else's. JWTs carry `deviceId` and refresh rows remember it.
- **First contact (metadata-privacy PR3.2, 2026-09-24; design §4.4). Client since PR3.1 slice (a): `BoxSession` publishes each device's request queue; the account's OWN devices send into one (the sibling address swap below), a friend's devices hand their queues through it (item 5 below), and since slice (f) a stranger's request travels through it (item 7 below).** `setRequestQueue { sid, sealPub }` → `requestQueueSet { success, error? }` publishes the caller's box REQUEST queue on the device its JWT names (never a payload device, the key-upload rule above); both fields are the canonical unpadded base64url of 32 bytes (`^[A-Za-z0-9_-]{42}[AEIMQUYcgkosw048]$`, the box's id spelling), stored on `devices."requestSid"` / `"requestSealPub"` (migration 0023). Codes: `invalid_payload`, `unknown_device` (no LIVE row — a revoked device stays unreachable), `internal`, `rate_limited` (+`retryAfterMs`, 30 / 15 min). `searchUsersResult` entries carry `id`, `username`, `tag`, `about` and NO photo field (no `profilePictureUrl`, no `profilePhotos`: a profile photo reaches a friend over the box, decision 138) and ADD `devices: [{ deviceId, bundle, requestSid, sealPub }]` and `authorization` (the same byte-exact record `deviceList` serves, null = not enrolled). `devices` = every device holding a published bundle and not revoked, oldest first (keyed on `key_bundles`, so a pre-Phase-1 device 1 with no `devices` row is served); `requestSid`/`sealPub` are null until that device publishes; each `bundle` is CLAIMED through the same path as `fetchPreKeyBundle` (one one-time pre-key spent per device per search, `preKeysLow` to that device's room), and a device whose bundle is gone by the claim is left out. An account that owes a replacement enrollment answers `devices: []`, `authorization: null`, nothing claimed (amendment (xlv) clause 2, as `getDeviceList`). Self still answers `[]`, before anything is claimed; a friend is answered like anyone, the full entry with its pre-keys claimed (owner decision 4; no friendship has a server row since step 5); with `BOX_ENABLED` off every entry has `devices: []` and `authorization: null` and nothing is claimed. `searchUsers` is throttled at the FETCH tier, 100 / 15 min (was 30 / min): a search spends pre-keys, so it may not drain a pool faster than `fetchPreKeyBundle`. The request sid is public BY DESIGN — anyone who can search the handle holds it — which is why a request queue drops its oldest and carries no media. **Named I2b exception:** `devices."requestSid"` is the same 32 bytes as `box_queues.sid` (the box must match the sid bytes on `send`, so no hashing scheme can separate them); design §5 lists per-device request sids as an accepted residual. A dump therefore links an account's device to its REQUEST queue (never a normal queue). **No push notifier is ever registered on a request queue (owner, 2026-09-24):** the device's one token would carry that link on to every normal queue of the device; a friend request waits for the next app open. **`getDeviceList` answers the caller's own account only since Phase 4 step 5 (below):** a friend's list comes from this `searchUsers` entry or over the box, never by id.
- **Own siblings' request queues (metadata-privacy PR3.1 sibling queues, owner decision 26, 2026-09-25).** `getOwnRequestQueues` (no payload) → `ownRequestQueues { success: true, devices: [{ deviceId, requestSid, sealPub }] }`: the CALLER's own account only — every live device holding a published bundle (the `searchUsers` device rule), oldest first, MINUS the calling session's device (a token without a device claim is device 1); `requestSid`/`sealPub` are null until that device publishes. No pre-key is claimed. Refusals: `internal`, `rate_limited` (+`retryAfterMs`, 30 / 15 min) — never an empty list, so a failure never reads as "no siblings". It names nobody the server does not already tie to the account; a device uses it to send its self-queue address as an E2E `queue_handoff` into each sibling's request queue. **Client (PR3.1 sibling queues part A, `BoxSiblingSwap` owned by `BoxSession`):** every device keeps ONE box SELF-queue (a normal queue, `QueueKeys.ensureSelf`, decision 27) in `e2e_<uid>_boxsib_v1` beside the siblings' addresses it learned (no backup carries the row, decision 28). Once the account socket is ready WITH a device id, the box is ready, the store is open, E2E is ready and the self-queue exists, it emits `getOwnRequestQueues` (payload `{}`); on `success` it sends each sibling with a published address whose recorded `ackedSelfSid` is not the current self sid ONE `queue_handoff {t, sid, sealPub}` — Signal to `(own userId, that deviceId)`, framed as an ACCOUNT-BEARING frame naming the own account, sealed to the sibling's request `sealPub`, `send` to its `requestSid`. Any answer (success or refusal) holds the next ask until the next account ready or a drop of the own verified device list (`EncryptionProvider.onDeviceListInvalidated` for the own id); `rate_limited` asks again after `retryAfterMs`; a failed handoff only records `BOX_SIBLING_HANDOFF_FAILED`. The receiver stores the address (replacing an older one; a store it cannot write now keeps the entry for the next offer and sends NO ack) and answers `queue_handoff_ack {t, sid}` — the sid it stored — into the sibling's SELF-queue as a normal frame; an ack is recorded only when `sid` is the receiver's CURRENT self sid, so a replaced self-queue is handed off again. A `'msg'` from a sibling is a SENT COPY (part B, E5; `to` above), read only when it was journaled from a self-queue (`BoxInboxEntry.viaSelfQueue`, decided at intake — the queue may have retired by the time it is read); on the request queue it is finished unread. A receiver whose own self-queue that sibling has not acked yet follows the ack with its OWN `queue_handoff` into the same self-queue, so a pair converges even when one side's `getOwnRequestQueues` raced the other's publish. A client publishes `setRequestQueue` and asks `getOwnRequestQueues` only once E2E is ready on that connect: a device still on the link gate holds the primary's token, and the server files a publish under the token's device (found live 2026-09-25: it overwrote the primary's request queue). A listed sibling whose `requestSid` is the caller's own is skipped; handoffs go only to devices the own VERIFIED list names live. **Rotation on revoke (part B, E6/E7, decision 27; `BoxSiblingRotation` inside `BoxSession`).** On e2eReady, own-list drop, box ready, store open and account ready, each device reads its own VERIFIED list (`MessagingProvider.ownLiveDevices`: null until E2E is ready and `socketReady` confirmed this device's id; the cache, else a fetch — independent of any box-covered peer). While this device is itself live, a `boxsib_v1` entry the list no longer names live is gone: with no self-queue it is pruned; otherwise ONE store write replaces the self-queue with a new one, prunes the gone entries and keeps the old queue RETIRING (still subscribed and read); the new address goes as a `queue_handoff` into each remaining sibling's self-queue, and the swap hands it through the request queues too. The swap notes an entry (`noteSibling`) before its first handoff to a device, so a sibling revoked before it ever answered still triggers a rotation. A retiring queue is deleted (`deleteQueue`) only once the box TTL (30 d) has passed since the rotation — never on acks: a sibling may still send into it (a copy built before it learned the new address, a second tab working from an older `boxsib_v1` read), and a `send` to a deleted sid answers ok, so such a copy would vanish; what the revoked device sends into it meanwhile is finished unread (revoked origin). An ack naming a sid of ours that is not current means the sibling learned an older handoff after the newer one (request and self queues are not ordered against each other): its recorded ack is forgotten and the swap asks again, so the current address is handed to it after the stale one was read. Residuals: a sibling still on the old address when the TTL ends loses what it sends there (a reconnect may also delete an expired queue before the box has pushed its last frames); every device of an account shares ONE identity key, so a revoked device can still pose as a live sibling on the public request queue (open owner question O6). **Unreadable sibling frames (E8):** a frame from an origin the own list names REVOKED is finished at once; an ABSENT origin, an undecided one (own list not cached and its fetch fails) or a missing session is held only on a self-queue and only for 30 d since intake, then finished; a missing session re-keys that sibling from our side once per session (a fresh `queue_handoff` is a PreKey message); a sent copy naming a peer this device holds no chat for waits the same 30 d (`BOX_SIBLING_COPY_EXPIRED`). The journal prune never removes an unconsumed row, so these caps are what bound the hold.
- **Batched device lists (metadata-privacy PR3.1 item 5, slice (d), owner decision 47, E20a; own id only since Phase 4 step 5).** `getDeviceLists { userIds }` — 1..256 DISTINCT integers in 1..2³¹−1 — applies `getDeviceList`'s rules to each user in turn (the caller's own id only; the (xlv)/(l) replacement-owed refusal) and answers each served user with the SAME `deviceList { userId, authorization }` event; there is no batch answer event. A refused user (every id but the caller's) stays silent, one user's lookup failure does not silence the others, and an invalid batch (empty, over 256, a duplicate, an id out of range or not an integer) is refused whole, in silence — so a client must treat a user it asked for and never heard about as "cannot verify", exactly as for `getDeviceList`. Throttled 60 / 15 min in its OWN bucket (`getDeviceList` stays 300 / 15 min); a throttled batch gets the generic `error { message: 'rate_limited', event, retryAfterMs }`, as `getDeviceList` does.
  - **Since Phase 4 step 4 (decisions 114 and 120, E114a–E114d; built 10-22) the client never names a friend's id to `getDeviceList` / `getDeviceLists`.** A friend's device list is the one held (kept across restarts), else ONE `searchUsers` of its handle per process (`lookupBoxPeerList`; a friend is answered like anyone with the box on); the request queues of its devices come from that same answer and are kept in RAM for the process. A friend with no route yet, a live device it holds no address for and a handoff to it due (not acked, never handed or handed 24 h ago) is looked up once per process. A lookup that could not be made yet (E2E not ready) spends nothing and is asked again on the next pass; one that was made and failed (spent, unanswered) is logged once per friend and error type (`BOX_FRIEND_HANDOFF_FAILED`, stage `lookup`). The OWN list is still asked by id: it names only the caller, and the server must keep answering `userId == caller`.
  - **Bounds of that lookup (spec review of step 4, E114m–E114p; client only, nothing new on the wire).** "ONE `searchUsers` per process" is the FIRST lookup of a friend: an event buys one more (a `sessionRebuildNeeded`, a peer's newer-list claim, acknowledging a new key, the verify dialog's key; 0.2.69 asked `getDeviceList` by id at exactly those moments, so the server learns nothing new). A peer- or server-driven event is floored at 1 min and capped at 6 per friend per process, and every lookup, the first included, sets that floor; a person's act (acknowledging, the dialog) has neither, being paced by the person. Where no lookup may be made the held list stands instead of being dropped. A lookup nobody answered (a timeout) is asked again by the next fetch, up to three times in a row (E114p), so an event that dropped the list does not leave the friend with none until a restart. The handoff pass's lookup of a friend for its request queues is also held to once per 24 h ACROSS processes (the device-local row `e2e_<uid>_boxlook_v1`, never sent, in no backup); a stamp from a clock that went back is replaced by the lookup it makes due, so that costs one extra lookup and not one per start.
- **One-time pre-keys belong to a PUBLISHED identity, and the order is load-bearing (2026-08-19).** `uploadOneTimePreKeys` is refused with `error { message: 'identity_locked' }` when its `identityPublicKey` is not the account's published one — otherwise a session whose bundle the registration lock just refused still upserts over the legitimate device's `keyId` slots, and while those rows are never SERVED (the fetch filter pins the published identity) the victim's pool is emptied until a peer fetch triggers `preKeysLow` (proven live 2026-08-18, user 168). - **Server-held contact backup (REST, metadata-privacy PR2.4, 2026-09-20).** `GET /backup/contacts` and `PUT /backup/contacts`, both `JwtAuthGuard`. **`GET` is throttled 30 / min, `PUT` 10 / min** (`contact-backup.controller.ts:25, :39`) — the PUT limit tracks the client's 5 s upload debounce, not the global ceiling, because every accepted PUT rewrites a 2 MB TOAST column and a permissive limit buys an authenticated account cheap WAL and dead-tuple churn. Size a retry loop against 10, not 30. One row per account, and the server never parses `blob` or `wraps` — it is an opaque store.
  - `GET` answers **404** when the account has no row. That is the ANSWER, not a failure: it is what tells the first client to mint the salt and the content key. A client MUST treat every other non-200 as unknown — reading a 502 as "no backup" lets a second device mint a second salt and orphan every other device's wrap. `200` is `{ v, rev, salt, ckId, wraps: [{kind:'password'|'phrase', ct}], blob, updatedAt }`.
  - `PUT` takes `{ v:1, baseRev, salt, ckId, wraps[], blob }` and answers `{ rev, updatedAt }`. **`rev` is optimistic concurrency over the WHOLE triple `(ckId, wraps, blob)`** — `baseRev` is the rev the client read, `0` means "I expect no row", and a mismatch is `409 { error:'stale_backup', rev }` with NOTHING written. That is what makes a partial write (a new blob beside another device's stale wraps, i.e. a row nobody can open) structurally impossible; the client re-GETs, re-merges and retries once, and never "forces" a write.
  - **The salt is minted once and is then immutable** — a PUT carrying a different one is `409 { error:'salt_mismatch' }`, nothing written, because every other device derived its wrap key under the stored salt.
  - **A no-op PUT does not bump `rev` and does not re-stamp `updatedAt`.** Identical `version`+`ckId`+`wraps`+`blob` at the right `baseRev` returns the current pair and writes nothing. This is the `key_bundles.updatedAt` lesson (`docs/agents/traps.md`): a timestamp that moves on every reconnect IS a per-account presence clock, which is the thing this PR series exists to remove.
  - Express's JSON body limit is **4 mb on `/backup/contacts` ONLY** (`backend/src/main.ts:33-64`), never globally: body parsing is express middleware, so it runs before Nest routing, `JwtAuthGuard` and `HttpThrottlerGuard`, and a global raise would let anyone buffer and `JSON.parse` 4 mb at `POST /auth/login` before a single check ran. Every other route keeps express's 100 kb default. The mount MUST stay a NAMED wrapper function (`contactBackupJsonParser`): `ExpressAdapter.registerParserMiddleware` skips Nest's own global parser when a layer named `jsonParser` is already on the stack, which is exactly what a bare `json()` returns (`traps.md`). The DTO caps `blob` at 2 000 000 chars; the default 100 kb silently 413'd an account with many contacts.

  - Verbs: `createQueue {v, kind:'normal'|'request', authPub, sig}` → `{ok, rid, sid, nid}` (idempotent per `authPub`: the same key gets the same queue back; the same key with the other kind is `invalid_payload`) · `send {v, sid, blob, mode?}` → `{ok:true}` | `queue_full` | `quota_exceeded` (the global ceiling; unsigned: the sid is the bearer credential). `mode` (owner decision 61, E61a, 2026-09-28) is absent for an ordinary send, else `'live'` or `'quiet'` (anything else `invalid_payload`): `live` is never stored, counted (queue cap, ceiling) or woken for — pushed once as an ordinary `msg` only if the queue is NORMAL (a request queue's sid is public and first contact is never live, so it is no free channel into its owner's socket) and the rid's subscribed socket is attached AND has room in its 16-unacked window, else dropped, and `{ok:true}` either way (no presence oracle), never re-pushed on a later subscribe; `quiet` is stored and pushed exactly like an ordinary send (`box_msgs.quiet`, migration 0025) but never schedules a notifier, neither at send nor in the socket-gone wake · `subscribe {v, subs:[{rid, sig}] 1..256}` → `{ok:true, refused:[{rid, code:'auth_failed'|'limit'}]}` (each entry stands alone, refusals in frame order; `limit` = past the socket's rid cap, below) · `ack {v, rid, id, sig}` → `{ok:true}` (deletes; acking a gone id — or a `live` one — is `ok`) · `deleteQueue {v, rid, sig}` → `{ok:true}` (messages + notifier go too) · `registerNotifier` step 1 `{v, platform:'fcm'|'webpush', token ≤4096}` → `{ok, state:'challenged'}` (unsigned, names no queue), step 2 `{v, code, queues:[{nid, sig}] 1..256}` → `{ok:true, refused:[{nid, code:'auth_failed'}]}` (owner decision 34, 2026-09-25).
  - **Signatures**: pure Ed25519 over `"umbra.box.v1" 0x00 ‖ verb 0x00 ‖ u8(len sockId) ‖ utf8(sockId) ‖ F`, `sockId` = the socket.io id of THIS connection, so a signature is dead once its connection closes (no clock, no nonce store). `F`: createQueue `kind(0x01 normal|0x02 request) ‖ authPub` (proof of possession) · subscribe/deleteQueue `rid` · ack `rid ‖ id` · registerNotifier step 2, per entry, `nid ‖ 0x02 ‖ code`. Verified with the queue's stored `recipientAuthPub` (by rid, or by nid for the notifier).
  - **No oracles**: `auth_failed` is ONE answer for an unknown rid/nid, a wrong signature and a wrong or expired code — so a repeated `deleteQueue` reads `auth_failed`, which a client treats as "already gone". A `send` to an unknown or deleted sid answers `{ok:true}` and drops the blob (no block oracle) — and at the global ceiling it answers `quota_exceeded`, exactly like a live sid.
  - **The one push, `msg {rid, id, blob}`**: one blob per frame, at most **16 unacked per socket** (each `ack` releases the next), round-robin across the socket's rids, oldest first within a rid. The NEWEST subscriber of a rid wins it; the stale socket's in-flight copies are released, not acked. **At-least-once**: an unacked message is pushed again after the next subscribe, so the client dedups (PR2.1 wire id) and must ack even a blob it cannot open, or it holds a window slot forever. The subscribe ack precedes the backlog.
  - **Bounds (I3)**: normal queue 128 (then `queue_full`; the client pauses that device and never retries the frame, E93a), request queue 50 (drops the OLDEST — first contact is never blocked by whoever holds the public request sid); messages expire 30 d, media 14 d; a queue never subscribed within 24 h (`claimBy`) and a queue not subscribed for 90 whole UTC days (`touchedDay`) are reaped with their messages (`BoxReaper`, every 10 min).
  - **Global ceiling (owner decision 30, E12, item 9 2026-09-26)**: the whole box holds at most **60 000 undelivered blobs and 2 GiB of media** (rung sizes). Past it a `send` answers `quota_exceeded` and an upload `429 {error:'quota_exceeded'}` from the headers — for an unknown sid too, so the refusal tests no sid; the one send still taken is into a FULL request queue, whose eviction replaces a message. **Reserved band (G5 BOX-CEILING-DOS, 2026-09-29): only the lower 30 000 blobs / 1 GiB are OPEN to every store; above them only a store into an ESTABLISHED normal queue is taken.** A normal queue is on probation until its creation UTC day + 7 (`box_queues."probationUntil"`, migration 0026) and established by its owner's first ack of a stored message, or first subscribe, on or after that day (the subscribe half, G5 review 2026-09-29: behind a full open band a probation queue stores nothing to ack, so ack alone would keep it on probation for good); a request queue never is (its sid is public). A new normal queue or a request queue therefore answers `quota_exceeded` once the open band is full, while friendships older than a week keep sending, uploading and receiving receipts; an unknown sid answers like an established queue (a block deletes a friend's, so the reserve must not test it). Room comes back as messages are acked, swept, deleted or reaped and media expire. Kept as running totals in the one-row `box_totals` (migration 0024), bumped by a conditional UPDATE in the same transaction as the row it counts — the bound (whole ceiling or open band) read from the queue row locked in that transaction — never a count over the tables; the numbers are injected (`BOX_CEILING`: `msgs`, `mediaBytes`, `openMsgs`, `openMediaBytes`) so the suite drives them small.
  - **Per-socket rid cap (E10)**: a socket holds at most **1 024** subscribed rids (≈ 1 000 contacts plus the self and request queues). A `subscribe` entry that would pass it is refused alone as `{rid, code:'limit'}` — the rest of the frame proceeds, as with `auth_failed` — and claims nothing; a rid the socket already holds costs nothing, and one a newer socket takes over frees its slot. Concurrent frames on one socket cannot overshoot (the cap is re-checked at attach; an entry refused only there was already claimed by its owner's signature). The client (`BoxClient._subscribeChunks`) reads `limit` as NOT gone: the rid stays in its resubscribe set, is never reported on `lostQueues` nor in `subscribe`'s refused list (every caller reads a refusal as "gone" and would drop the queue), and the next connection offers it again.
  - **Throttles, per client IP** (`X-Real-IP`, IPv6 widened to its /64 in the box only), per 15 min: `createQueue` 120, `send` 1500, `subscribe` 60, `ack` 3000, `deleteQueue` 300, `registerNotifier` 30; `POST /box/media` 300, `GET` 3000. The refusal rides the event's own ack. **An `ack` naming a message pushed to THIS socket and not yet acked skips the `ack` limit, once per push** (G5 BOX-ACK-BUDGET, 2026-09-29): the client acks every delivery, junk included, so without it a sender flooding a public request sid spent its owner's bucket and the refused acks held every queue on that socket behind a full window; only that socket learned the id. A stale id, a repeat or a forgery still counts. Abuse visibility: the sweep logs refusal COUNTS, never an address — per throttled event, plus the quota refusals (E11) `send:ceiling`, `mediaUpload:ceiling` and `mediaUpload:budget`.
  - **Push notifier** (one challenge per TOKEN, owner decision 34): step 1 pushes `{type:'notifier_challenge', code}` to the token and stores NOTHING durable; only step 2, bringing that code back, writes a `box_notifiers` row for each entry its own queue key signed (a stolen token cannot be attached to someone's queue: the code reaches the token's holder only). A code never pushed or older than 10 min refuses the WHOLE frame `auth_failed`; a bad entry (unknown nid or wrong signature, one answer) is refused alone, the rest activate; a repeat is `ok` and rewrites nothing. Pending codes are kept per code, not per token or connection, so a reconnect between the steps or a stranger challenging the same token voids nothing. A `webpush` token is `PushSubscription.toJSON()` whose endpoint must be https on `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com` or `*.notify.windows.com` — the box POSTs to it, so an open endpoint would be SSRF from an unauthenticated verb. An FCM wake-up is `{type:'new_message'}` and nothing else (its `data` transits Google readable); a Web Push wake-up (owner decision 77, superseding D6) is `{type:'new_message', n, c}` inside the RFC 8291-encrypted payload: `n` = the queue's nid, base64url (the form the client stores as `ContactQueue.nid`), `c` = the queue's messages delivery would hand out (not expired) that may wake (not `quiet`), counted when the push goes out — not `box_queues.msgCount`, which counts quiet rows too. A Web Push wake-up is never sent when that count is 0 (everything was acked or expired during the coalescing wait — a resumed page's new socket acks what its old socket held before the old socket's detach wake-up flushes; driving a frozen page showed a `c: 0` push alerting for nothing), so `c` ≥ 1 on the wire; the SW still reads a lower value as 1. Nor is it sent when every message that waits was already announced by an earlier Web Push wake-up of that nid (kept in memory, compared by the newest waiting message's arrival time read in the same statement as the count): a frozen page is woken 2.5 s after the send, and its socket's ping timeout ~40 s later would have woken it again for the same message. A message that arrives after the last wake-up wakes again. Relay TTL of a Web Push (`box-push.transport.ts`): a challenge 600 s (`BOX_CHALLENGE_PUSH_TTL_S`; its code dies at 10 min), a wake-up 86 400 s (`BOX_WAKE_PUSH_TTL_S`); FCM keeps its own defaults. Wake-ups are coalesced per nid (2.5 s / 10 s), sent when a blob lands on a rid no socket owns — AND when the socket that owned a rid goes away while the queue still holds a message delivery would hand out (not expired; E9 drive, 2026-09-25): a silently dead socket is detached only at the ping timeout (~40 s measured), and every blob stored meanwhile was handed to it instead of to a push. A Web Push wake-up also follows a send handed to a socket that owns the rid when, at the end of the coalescing wait, something that may wake still waits (a frozen page, iOS, keeps its socket ~45 s and never acks); such a window never wakes an FCM device: native is unchanged. One ordinary (socket-less or disconnect) schedule in the window makes it an ordinary wake-up for an FCM device.
  - **Client push registration (E9, 2026-09-25; `BoxNotifiers`, `PushBoxSource`).** Every NORMAL inbound contact queue (`ContactRecord.queues`) gets a notifier, except a `blocked` or `former` contact's (decision 35: the box cannot know a block, and a blocked peer holding the sid could ring an offline device; one blocked AFTER activation keeps its notifier until the queue is deleted); the request queue (decision 2) and the self-queues, current or retiring (decision 32), never do. ONE challenge per pass proves the token for every owed queue (decision 34): challenge, await the code (30 s), activate the owed queues 256 to a frame, recording each frame as it lands; a first frame refused `auth_failed` carries a stray code from an earlier challenge and the next code is awaited; a nid refused in a batch is gone and is not offered again by that `BoxNotifiers` (each offer costs a push); nothing owed means no challenge; no code ends the pass (push does not reach this app), and so does a step-1 `invalid_payload` (the box refuses the TARGET); either way that target rests 15 min, because a web page re-runs on every return to the screen and the budget is shared per IP; `rate_limited` resumes after `retryAfterMs`. What is active is kept per push target (SHA-256(platform 0x00 token)) in `e2e_<uid>_boxntf_v1`, so a queue is activated once per token, not once per launch; a new token re-registers every queue. Runs on box ready, store open and target change. Web: the token is `{endpoint, keys, expirationTime}` (the account-side `userAgent` is refused by the box parser), a challenge is taken only by a VISIBLE page, the source is inert where `navigator.serviceWorker` is undefined (an insecure context, some in-app WebViews — touching it threw and left the box session half-wired, found in review), and the push SW forwards the code to every open page (`box-notifier-challenge`) and posts no notification (decision 137, 0.2.78; before it, a "Setting up notifications" card flashed, since Safari revokes a subscription after 3 silent pushes). Native: the FCM token, codes from `FirebaseMessaging.onMessage`, only while the app is resumed.
  - **HTTP media**: `POST /box/media`, header `Box-Sid` (never in the URL), `application/octet-stream` with a `Content-Length` of exactly one rung (4/16/64/256/1024 KiB, 4/16/32 MiB; the 32 MiB rung keeps today's 20 MiB plaintext file sendable once padded) → `201 {id, bucket, expiresAt}`; any other size → `413 {error:'bad_size'}` decided from the HEADERS, before one body byte is read. **No body parser runs on this route** (the same middleware-before-guards reason as the backup limit above): the controller reads the body only after `HttpThrottlerGuard` and the size check, streams it to disk, and drains it for an unknown sid (which still gets `201` with an id that is never stored — answering before the body arrived would reveal a dead sid). A request-queue sid, a spent daily budget (1 GiB per normal queue per UTC day, charged at the rung size; owner's number 2026-09-23) or the global media ceiling (above; any sid) → `429 {error:'quota_exceeded'}`, body unread; throttled → `429 {error:'rate_limited', retryAfterMs}`. The charge, the global total and the `box_media` row are one transaction, written before the body is read. `box_media` has NO rid column. `GET /box/media/:id` → `200` bytes with `Cache-Control: no-store`, or `404`. Files live in `MEDIA_DIR/box/`, never in the old `msgs/` directory (no code reads, serves or sweeps it since step 5).

The `/box` socket rides `location /socket.io/`.
  - **Client (PR1.2, `frontend/lib/services/box/`; wired by PR3.1 slice (a): `ConnectionProvider` holds one `BoxSession` per signed-in account — created at `connect()`, resumed on a same-account reconnect, its socket PROBED on every app resume (`BoxClient.checkAlive`, whatever the account socket claims: the server pings every 25 s, so once the page had 2 s to read what its suspension held back, a socket that heard nothing since the resume and nothing for 30 s is replaced, one silent for less is judged again at 30 s; a suspended iOS PWA kept a dead box transport that socket.io reported connected until its ping timeout, so sends timed out red and the box handed stored messages to that dead socket instead of a push; a live socket is never touched, decision 76, E76b), closed on `disconnect()`, disposed on logout — which connects the `BoxClient`, loads-or-creates this device's request queue (`QueueKeys.ensureRequest`, stored as `e2e_<uid>_boxreq_v1`) and its self-queue (`QueueKeys.ensureSelf`, `e2e_<uid>_boxsib_v1`, same create → claim → subscribe and drop-and-replace-once rules) and publishes it via `setRequestQueue` once per (device id, sid) PER SESSION after both sockets and the contact store are ready — the dedupe is RAM-only, so every launch, tab and reload publishes again and the server overwrites the same value; a store that opens late (a web vault booted locked, then unlocked) triggers it too; a refused request rid on resubscribe is replaced and re-published).** `BoxClient` owns its own `/box` socket (`enableForceNew`, no `setAuth`, no library reconnection) driven by its own `ChatReconnectManager(requiresToken: false)`. It signs over the NAMESPACE socket's `id` through `BoxSigner` (asynchronous): on the web the browser's WebCrypto Ed25519 (`box_signer_web.dart`; 256 signatures ~20–40 ms), falling back for the session to pure-Dart `ed25519_edwards` where the browser has none or `crypto.subtle` is absent (insecure context); off the web pure Dart. The pure-Dart signer signs one at a time, each after one event-loop turn (only one turn pending, so a later timer or frame waits at most one signature), because signing a 256-rid chunk back to back froze the web UI for ~2.6 s (dart2js ≈ 8–11 ms/signature). A frame is built after signing and dropped as `disconnected` if the socket changed meanwhile, so a signature over a dead id never goes out; it NEVER emits while not connected (socket.io's `sendBuffer` would replay a signature bound to a dead id) and fails every call in flight `disconnected` on a drop (socket.io never fails a pending ack). Every connection re-signs `subscribe` for the whole set in chunks of 256 and is `ready` only after the last chunk answered; a chunk that does not answer ok drops the connection into the reconnect backoff; a refused rid leaves the set and is reported on `lostQueues`. Answers are `BoxOk` / `BoxRefused(code)` / `BoxUnknown(offline|timeout|disconnected|malformed)` — unknown is never a refusal; `deleteQueue` → `auth_failed` IS success (gone). Queue material lives in the peer's contact record as `ContactQueue {rid, sid, nid, authPriv = Ed25519 seed‖pub (64 B), sealPriv, sealPub}` (`QueueKeys.ensureInbound`, one per friend: the record's queue if it holds one, else create → store → subscribe; a queue the store did not keep, or one another tab stored first, is deleted again).
  - **Blob seal (client ↔ client, `QueueSeal`, design §4.3).** `blob = 0x01 ‖ ephPub(32) ‖ IV(12) ‖ AES-256-GCM(frame) ‖ tag(16)` = exactly 16384 B; key = HKDF-SHA256(ikm = X25519(eph, sealPub), salt = 32 zero bytes, info = `"umbra.box.seal.v1" 0x00 ‖ ephPub ‖ sealPub`, 32 B); `frame = uint32be(len) ‖ body ‖ zeros`, 16323 B, so a body is at most 16319 B. The target is the QUEUE's raw 32-byte X25519 key, never the account identity key (linked devices share it, so a revoked device could open every seal). A fresh ephemeral per blob; a low-order point (seal or open) answers null, never a key everyone can compute.
  - **Sealed body on a NORMAL queue (`BoxFrame`, PR3.1 slice (b), owner decision 12):** `u8 v=1 ‖ u8 kind ‖ u16be senderDeviceId ‖ raw Signal bytes` — binary, because base64-in-JSON spends a third of the 16 319 B; kind 2 = whisper, 3 = PreKey; device 1..100; kinds 0x12 (whisper) and 0x13 (PreKey) are the ACCOUNT-BEARING frames a REQUEST queue carries (PR3.1 sibling queues): `u8 v=1 ‖ u8 kind|0x10 ‖ u16be senderDeviceId ‖ u32be senderUserId (≥ 1) ‖ raw Signal bytes`, four Signal bytes fewer; kinds 0x32 (whisper) and 0x33 (PreKey) are LIST-BEARING account-bearing frames (slice (e), decision 50, E50b): `u8 v=1 ‖ u8 kind|0x30 ‖ u16be senderDeviceId ‖ u32be senderUserId ‖ u16be len (≥ 1) ‖ len bytes of the sender account's authorization record as JSON ‖ raw Signal bytes (≥ 1)` — a friend's handoff on a request queue carries its account's device list OUTSIDE Signal so it is judged before Signal sees the frame; kinds 0x52 (whisper) and 0x53 (PreKey) are CLAIM-BEARING account-bearing frames (slice (f), E15b): the list-bearing layout with bit 0x40 instead of 0x20, whose `len` bytes are the claim `{"u": username, "g": tag}` as JSON (no photo) — a frame carries a list or a claim, never both; every other kind from 0x10 stays reserved and unreadable. The claimed account only picks the Signal session to try — the decrypt authenticates it. No sender account on a normal queue: the queue is per peer, and an account-bearing frame on one is dropped. The composer's limit (`AppConstants.maxEnvelopeBytes`, 14 000 envelope bytes, every chat — decision 18) is sized so every text the app lets you send fits one frame: the longest accepted text with a link preview, as a PreKey message, fits (`box_frame_test.dart`).   - **Receive (`BoxInbox` + `MessagingProvider.consumeBoxEntry`, slice (b)).** `BoxSession` subscribes every contact queue once the box is ready AND the contact store is open. Each delivery: find the queue (store records) → open the seal → decode the frame → JOURNAL it (`e2e_<uid>_boxin_v1_<rid>.<id>`, beside the contact rows, sealed on web) under a LOCAL message id (decision 14: ≥ 2^48, from the counter `e2e_<uid>_boxlid_v1` bumped under the store's cross-context lock and never lowered, above any local id a record/retired set/ledger names) → ACK → offer to the reader. The journal comes BEFORE the ack (a delivery the journal could not take — store closed by a re-lock, a refused write — is held in RAM and retried by the next drain, never left to the box, which re-pushes only after a resubscribe); the ack comes BEFORE the read and whatever the reader says, on its OWN chain — journal + ack never wait for a read, reads run one at a time on a second chain in arrival order (a withheld sender device or unready E2E waits in the journal, not in one of the 16 window slots); an ack the box refused or never answered is sent again — a journal row stays `acked:false` until confirmed, every drain re-acks those, and a refusal arms a retry drain (`retryAfterMs`, else 30 s); a dropped blob whose ack was refused is held and taken again the same way. A blob pushed again after its ack answer was lost finds its journal row and is only acked: Signal never sees a ciphertext twice. Acked and dropped: a blob that does not open, a frame this build cannot read, an account-bearing frame on a normal queue, anything on the REQUEST queue except an account-bearing frame naming THIS account (a sibling's handoff) or a FRIEND's (its queue handoff, item 5 below; journaled with `req: true`); a stranger's only as a claim-bearing request (item 7), and a delivery on a queue no record holds any more (acked with the box client's own key, then forgotten). The reader hands a delivery back at once while E2E is not ready (the E2E-ready drain offers it again), decrypts under the local id (the replay-cache key; a finished box entry — stored, duplicate, unknown type, empty — drops its replay row, which holds plaintext); a failed decrypt follows `decideDecryptionFailure` — the peer is asked to re-key on Bad MAC / identity reset (and once on no-session; a no-session entry stays in the journal and is offered again by a later drain), a message that will never decrypt shows `[Decryption failed]` in RAM, a duplicate shows nothing, anything that may heal is offered again. It routes on `t` (`'msg'`, and item 4's `react`/`pin`/`edit`/`del`, below; an unknown type is dropped), drops a wire id a delete-for-everyone tombstoned (`EncryptionService.boxTombstoned`, item 4) or the device already holds from that sender (`EncryptionService.wireHeldByOther`), stores the plaintext and shows it — sound only for the chat on screen (owner decision 11). The journal row goes only once the plaintext record is PROVEN on disk (read back, since the save swallows a refused commit); until then the message is shown from RAM and the next offer stores it without a second decrypt. Drains run on box ready, store open, reader wired and E2E ready. A delivery on this device's self-queue or a sibling frame from its request queue is journaled under the OWN user id and read BEFORE the contact-record refusals (the own account has no record): the same E2E-ready wait and accept gate (the sender device must be live in the OWN verified list), decrypt with `(own userId, senderDeviceId)`, the same retry-or-finish policy, but no re-key request (`requestSessionRebuild` names an account, and every own device would mark its device-1 session). A handoff or ack is never shown; a SENT COPY (`t: msg` with `to`, read only when journaled from a self-queue) is filed and shown as the account's own sent row (Own siblings, above).

Receipts and typing skip a paused device. When every peer device is paused, a send fails for a retry with nothing sealed (E93b). When NO peer device took its frame the row fails for the ordinary retry, which reuses the send token — kept across a same-user reconnect — so a device that already holds the message drops the copy (`wireHeldByOther`).   - **Item 3: pings, replies, timers and media over the box (PR3.1 decision-22 slice, owner decisions 40–44, 2026-09-26).** New envelope fields, read ONLY by the box reader:

    - The route is decided BEFORE the upload. The AES-GCM ciphertext is framed `uint32be(len) ‖ ct ‖ zeros` on the smallest ladder rung ≥ 4 + len, uploaded ONCE with `Box-Sid` = the first live peer device's queue, and the same id goes to every peer frame and sibling copy.
    - A refused or unanswered upload fails the row.
    - In-app the attachment is `mediaUrl: box:<id>`, which is only ever sent over the box (a retry whose route is gone fails, decision 25). A retry after the upload re-sends frames only (same id, key, IV and wire id). Before the upload, a retry re-uploads the same in-RAM ciphertext; a restart loses it.
    - Every device keeps the UNFRAMED ciphertext locally (native `<appSupport>/box_media/<userId>/<id>`, web IndexedDB `umbra-box-media`); the key lives only in the sealed record.     - Destroying the record deletes the copy.
  - **Item 4: reactions, pin, edit and delete-for-everyone of a message (owner decisions 45–46, E19a–E19l, 2026-09-26).** Actions go ONLY over the box, as envelopes `{t: 'react'|'pin'|'edit'|'del', tg: {s, w}, ts, senderListInfo, to?}` plus `e` + `on` (react), `on` (pin), `content` (edit), and never a `msgId`:

A friend's reference naming a media id this device already holds for the own account or another contact is refused, and a file a held reference still names is never deleted. The file is downloaded at once (`BoxMediaFetcher`, decision 40's retries; a file larger than 256 KiB or not a JPEG of at most 1024 px is refused unread), its ciphertext kept in `BoxMediaStore`, and the contact record holds the reference (`ContactRecord.avatar`, beside the legacy read-only `avatarUrl`); the contact backup carries the reference only, and a restore applies the backup's own reference when it outranks the one held. Migration: the first launch with this build, an account with a server photo (`GET /users/me` `profilePictureUrl`), no reference of any kind (a removal counts) and no earlier move downloads it, uploads it with `r = 1` and stops; removing the photo before that writes a cleared reference and settles the move.
    - **Account delete (decision 113, E114h–E114i).** `AuthProvider.deleteAccount` verifies the password (`POST /users/verify-password`), then `MessagingProvider.goodbyeToBoxFriends` sends `{t: 'goodbye'}` (quiet, no `to`) to every device of every friend this device holds an address for, then `BoxSession.retireAccountQueues` deletes every queue the device holds (each contact's inbound queue, the self-queue, retiring self-queues, the request queue), all inside a 10 s budget that never holds the delete, and only then `DELETE /users/account`. Our siblings are not told (they lose their session at the delete). A friend's build before 0.2.68 ignores the goodbye; a friend with no address held gets none; the box answers a `send` to a deleted queue `ok`, so nothing proves delivery.
  - **Item 8: receipts and typing (slice (g), owner decisions 33, 61–62, E61a–E61f, 2026-09-28).** One device-local switch in Privacy & Safety (`SettingsProvider.receiptsAndTyping`, pref `receipts_and_typing`, default OFF) turns on delivered ticks, read ticks and typing on box chats; the row shows only once this device is on the box (`boxFriends.onBox`, appearing live on `onBoxReady`; G5 owner call 2026-09-29), since before that it does nothing. OFF, a device sends no `rcpt`/`typ` and ignores every one it receives (mutual, the Signal model), so box messages show only ✓ until both sides turn it on.
    - Envelopes: `{t: 'rcpt', k: 'd'|'r', w: [1..100 wire ids]}` names messages the RECEIVER of the receipt sent; `{t: 'typ', k: 't'|'v', on: bool}` (text, voice recording). Anything malformed, one bad wire id included, is dropped whole.
    - Send (`MessagingBoxReceipts._sendBoxSignal`): the peer half of `_boxRoute` only (`peerOnly`: the addressed live peer devices under decision 101's rule below, never a sent copy to our siblings), best effort — no retry, no failure surface. `rcpt` is `mode: 'quiet'`, `typ` is `mode: 'live'` (above).
    - Delivered: one `rcpt d` per peer per drain (`BoxInbox.onReadsIdle` → `onBoxReadsIdle`), naming the peer's box messages proven stored in that drain and not already reported read, in frames of ≤ 100. Read: one `rcpt r` from `markConversationRead` (and after a chat's local rows merge), only for the chat on screen with the app visible, naming the peer's box messages not reported read yet; once a device took it those rows keep `tick: read` in their record (never reported again after a restart), and a receipt no device took is sent again the next time the chat is shown, once this connect's device lists are ready (`BoxDeviceListRefresh.onReady`), or when the app becomes visible again. A peer message shown while the switch is OFF is marked read here and never reported (decision 63). ✓ is sent or delivered, ✓✓ read.
    - Typing: `on` at most once per 5 s per chat while the composer changes; voice on each recording change and `on` again every 5 s while recording. The receiver shows text typing until 6 s after the last `typ`, voice until `off` or 12 s after the last `on` (a `live` `off` can be lost or overtaken); the peer's next message clears both.
    - Receive: only on the peer's queue (a self-queue copy is dropped, `BOX_SIBLING_COPY_REFUSED`); a `rcpt` moves OUR box messages it names in that peer's chat forward only (sent → delivered → read), kept in the record as `tick` so a restart keeps it; a wire id not held here is dropped, never parked.
  - **Offline linked devices (owner decisions 101–103, 2026-10-16).** Every frame is inside Signal; the only thing the box sees that it did not before is a catch-up blob: one box media upload against a returning device's self-queue, made by a sibling soon after that device comes back (14-d TTL; no client route deletes media earlier).
    - `rl: 1` rides a frame a device sends to a FRIEND's device (message, action, retry, receipt, typing, handoff, ack, `list_update`, goodbye, timer): "this device relays". A device sends it only while every live sibling in its own verified list was heard on our self-queue sending `alive`, `sync_req`, `sync_resp` or `relay` (E101b: an older sibling would finish a relayed copy unread); a single-device account always does. The friend keeps what each authenticated frame says per (user, device) on that device's address (`ContactOutbound.relays`, a frame without `rl` clears it), never in the contact backup.
    - Coverage (amends decision 16 for friends only): a friend is box-covered when every live device has an address (as before) OR at least one does and an addressed live device sent `rl`. Peer frames go only to addressed devices; when a live device was left out, the peer `json` of a message or action carries `ad: [addressed device ids]` (1..100 ids in 1..100, else absent; a paused device counts as addressed; never in `copyJson`, receipts or typing). Own siblings' `own_uncovered` rule and first contact are unchanged.
    - Relay: a device that first stores a friend's message, or takes a friend's action, carrying `ad` sends `{t: 'relay', u: friendUserId, d: friendDeviceId, e: <the friend's envelope>}` quiet to each live own sibling missing from `ad` that has a self-queue address and a usable session (never a bundle fetch, never to a paused sibling). An edit or delete of someone else's message is not relayed. The sibling accepts it only from its self-queue and only for a `friend` contact, and reads `e` as if from `u` on `d`: dedup by `(u, wireId)` against a direct copy, E19b sender rules, E19k parking, the hidden-arrival card. A `relay` inside `e` is dropped; a relayed frame is never relayed again.
    - Catch-up sync (decision 102): a device back after more than 10 min off the box (a stamp every 2 min while on it, `e2e_<uid>_boxsync_v1`) sends ONE quiet `{t: 'sync_req', since}` (`since` = last stamp − 10 min, at most 30 d back) to one live sibling (most recently heard, then lowest id; a paused one is skipped unsealed and a full one moves to the next; with none asked the request stays owed). The answer `{t: 'sync_resp', since, count, boxMedia, mediaKey, mediaIv}` points at one AES-256-GCM box media blob uploaded against the requester's self-queue: the history-file payload (`fp-history` v1, `_decrypted_` records of local ids at or after `since` that carry a wire id, not tombstoned or expired), newest first, at most 1 MiB. Nothing to send sends nothing; a sibling is answered at most once per 10 min. Import dedups by `(sender, wireId)` and tombstones, takes fresh local ids from the allocator, and is quiet (no card, sound or receipt).
    - `{t: 'alive'}` (decision 103): no other field, own device to each live sibling, quiet, at most once per 24 h per sibling at the connect's list refresh and on an own-list change, only over a session already held and never to a paused sibling (a `queue_full` answer pauses it and counts as today's). Any frame from a sibling that decrypts on our self-queue stamps its last-heard time (`e2e_<uid>_boxalive_v1`, sealed on web, no backup); the primary (lowest live id) asks to unlink a sibling silent for more than 30 days.
    - Old builds ignore `rl`/`ad` and finish an unknown `t` (`relay`, `sync_req`, `sync_resp`, `alive`) as `BOX_UNKNOWN_TYPE`. A `sync_req` to an old-build sibling is therefore lost (the box took it). A friend relaxes coverage only for a device that sent `rl`, because an old build ignores `ad` and would never relay; and a device sends `rl` only while all its siblings read `relay`, because an old-build sibling would drop the relayed copy.
