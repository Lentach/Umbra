## Contracts

- E2E envelope: `{ content, messageType?, mediaUrl?, mediaDuration?, mediaKey?, mediaIv?, mediaWidth?, mediaHeight?, mediaThumbHash?, linkPreview?, senderListInfo? }`. Ciphertext format is `"{type}:{base64}"` (`3` PreKey, `2` Signal/whisper). Server stores `[encrypted]` plus metadata.
  - `senderListInfo` is `{ ownVersion?, ownListHash?, peerVersion?, peerListHash? }` — the sender's view of BOTH parties' device-list versions, hashed as SHA-256 (base64) over the DAK-signed `listCanonical` bytes exactly as transported (multi-device spec §5.2 layer 2, §12 amendments (xv)/(xvi)). It rides inside the plaintext, so the server never sees, stores or validates it, and it is attached to every message. A party the sender holds no verified list for is ABSENT from the object, never reported as version 0. On receive it is untrusted peer data: a bare claim NEVER alarms and never changes trust (I7); a claim newer than the recipient knows buys at most ONE rate-limited device-list re-fetch and is then discarded; a claim older than the recipient's own verified version (or the same version with different canonical bytes) is a split-view signal, recorded durably for the operator; skew about the recipient's OWN devices renders only the calm "syncing devices" note, never the identity-changed surface. Unknown envelope keys are ignored by `E2eEnvelope.parse`, so an older peer omitting the field is normal.
- Socket readiness clock: after socket auth completes, server emits `socketReady` with `{ serverTime: string, deviceId: number }`; `serverTime` is an ISO-8601 UTC instant stamped at that completion. `deviceId` is which device of the account this socket is (multi-device spec §5.3) — the client cannot derive it, and it is load-bearing twice over: a fan-out send must exclude its own origin device (the server refuses `self_envelope_for_origin_device`), and the self-sync receive law only scopes an own row's origin once this value is CONFIRMED rather than the §8 default of 1 (spec §12 amendment (xii)).
  - Why: this is the client's only trustworthy clock reference for gating destruction of expired message plaintext. Destruction requires a fresh observation (never extrapolated past 30 minutes) and `expiresAt` plus a 5-minute grace for the backend's per-minute cleanup cron.
  - Missing, stale, or unparseable `serverTime` fails silently closed: the client holds and never destroys expired plaintext — no error or log, while plaintext accumulates. This deliberate asymmetry accepts over-retention rather than permanent data loss: the server holds only ciphertext, which the client cannot decrypt after the Signal ratchet consumed the key.
  - Compatibility: older clients ignore the extra field; newer clients against older servers receive no usable clock and therefore never destroy plaintext on expiry.
  - In-session refresh: client emits `getServerTime` (no payload); server replies `serverTime` with `{ serverTime: string }`, same ISO-8601 UTC semantics. The client's sweep timer asks only when its last observation aged past the 30-minute extrapolation bound (floor-limited to one unanswered request per 5 minutes), so a connection that outlives the socketReady observation can still destroy expired plaintext instead of holding it until the next reconnect. An older server simply never answers and the client stays fail-closed.
- Local-plaintext reconciliation: client emits `getServedMessageIds` with `{ requestId: string, messageIds: number[] }` (≤500 ids); server replies `servedMessageIds` with `{ requestId, messageIds }` — the subset it would still serve that account through the history read path (row exists, caller is a participant, not hidden by them, not expired).
  - Why: the client DESTROYS the local plaintext of every id it asked about that is absent from the reply. That is the only mechanism that reaches messages deleted or expired before the metadata stamps existed — those records match no local rule and their server row is already gone, so nothing else would ever revisit them.
  - The reply is authoritative, so the server MUST stay silent on failure rather than answer with an empty list: an empty `messageIds` legitimately means "destroy all of them" (a fully cleared history). A missing reply purges nothing. `requestId` is echoed verbatim so a late or foreign answer cannot be applied to the wrong batch.
  - The existence check MUST remain at least as permissive as the history read path. A false "not served" is irreversible loss; a false "served" only defers cleanup. In particular it carries no `sender != me` or `deliveryStatus` predicate — either would report the caller's own outgoing history as gone.
  - Client throttles to one completed pass per 6 hours per account and only stamps completion when every batch was answered.
- Delete semantics:
  - Delete conversation: messages + conversation removed, friendship kept, WS `deleteConversationOnly`.
  - Unfriend: friend request + conversation + messages removed, friendship removed, WS `unfriend`.
  - Clear history: messages removed, friendship kept, WS `clearChatHistory`.
  - Delete for me: hidden for caller only, WS `deleteMessage mode=for_me`.
  - Delete for everyone: sender-only hard delete for both sides, clears pin, WS `deleteMessage mode=for_everyone`. **Sender-only covers the MEDIA unlink as well (2026-09-14).** The unlink used to run before the sender check, gated only by conversation membership, so a RECIPIENT emitting `mode=for_everyone` destroyed the sender's file on disk, was refused the row delete, and left a surviving message whose `mediaUrl` 404s forever (`chat-message.service.ts`, reproduced over the wire). A non-sender's request now changes nothing — not the row, not the disk.
- Edit message: sender-only text edit within 15 minutes, from ANY of the sender's devices (spec §5.7 + §12 amendments (xxx)–(xxxiv), Phase 2 T7). Inbound `editMessage { messageId, envelopes?: [{userId, deviceId, ciphertext}], encryptedContent?, senderListVersion?, recipientListVersion? }` — a FULL RE-FAN: one edited ciphertext per recipient device AND per sender's other device. A legacy single `encryptedContent` is still accepted and normalized to a device-1 envelope at ingest (§8), and is REFUSED like a legacy send once either party is enrolled. The server verifies sender + window + envelope shape + list freshness BEFORE any write, then in ONE transaction stamps `editedAt`, re-points `messages.originDeviceId` at the **EDITING** device, and **UPSERTs each envelope CONTENT-ONLY so its stamps SURVIVE** (durability F8: an edit is not an un-delivery, and the §4 projection must never regress). Today that means `deliveredAt`, the only envelope stamp any code path writes (`stampEnvelope`'s single call site, from `messageDelivered`); `readAt` is a declared column and a permitted `stampEnvelope` field that **nothing writes yet** — `markConversationRead` drives the ROW to READ and leaves the envelope alone — so do not build on it without writing it first. The conflict clause names `ciphertext` alone, so both are safe by construction. A device with no prior envelope gets one INSERTED — its `none_for_device` placeholder upgrades, never the reverse — and envelopes of devices dropped since the send are LEFT alone (the delete CASCADE is the only destruction path). Each device is then fanned ITS OWN ciphertext via `messageEdited { messageId, conversationId, content, encryptedContent, editedAt, originDeviceId }` at its newest socket; the editing device is the PRODUCER, so its echo carries `encryptedContent: null`. Refusals: `editMessageFailed { messageId, reason }` keeps its four codes (`not_sender`, `window_expired`, `not_text`, `not_found`) and gains the (v) shape codes (`duplicate_envelope_device`, `unknown_envelope_user`, `unknown_recipient_device`, `self_envelope_for_origin_device`); a stale list answers the EXISTING `deviceListStale` event. An edit NEVER mints or consumes a `sendToken`. **Receivers key their Signal session off `originDeviceId`, which is why an edit must re-point it** — the client adopts it before decrypting, and an own row edited by a SIBLING device is decrypted rather than merely reconciled.
- **`setDisappearingTimer` fans out to BOTH users' FULL device rooms (2026-09-14).** `setDisappearingTimer { conversationId, seconds }` writes `conversations.disappearingTimer` and then emits `disappearingTimerUpdated { conversationId, seconds }` to `userRoom(setter)` AND `userRoom(peer)` — never to the calling socket alone. The timer is conversation METADATA and the user room exists so every device sees metadata (`chat.gateway.ts:176-178`); the original `client.emit` told only the socket that made the change, so the setter's other linked devices kept displaying the DISPLACED value (field-found on a 3-device account). That is a stale safety promise — the user is shown a schedule that is no longer in force — which is the same harm `WsThrottlerGuard` avoids by refusing to echo an unapplied value. The timer is read at send time only (`chat-message.service.ts:345`, `data.expiresIn ?? conversation.disappearingTimer`), so a stale display never mis-stamps a row; it misinforms. Related lifetime law: the row is created with `expiresAt: null` and `expiresAt = now + ttl` is stamped only when the recipient READS it, with a 1-day never-read backstop; expired rows are HARD-deleted by an `EVERY_MINUTE` cron, media unlinked first.
- **Conversation METADATA fans out to every device of every party it concerns (2026-09-14, same sweep as the timer above).** The gateway's own rule is that ciphertext is per-device while "metadata keeps using the user room … so every device still sees it" (`chat.gateway.ts:176-178`), and four sibling handlers broke it by emitting to the ACTING socket instead of the acting user's room — so the actor's other linked devices were the only participants left uninformed. Now: `messagePinned` and `messageUnpinned` go to `userRoom(actor)` **and** `userRoom(peer)`; `conversationMuteUpdated` goes to `userRoom(muter)` **ONLY** — mute is a private per-account preference (`conversation_notification_preferences`, keyed `(userId, conversationId)`), so the muter's other devices must stop buzzing while the peer must never learn they were muted. Deliberately NOT changed: `openConversation` stays socket-local (opening a chat on someone's other device is not a sync, it is a hijack), and the `conversationsList` refreshes after delete/leave stay caller-local because each device rebuilds its own list on connect.
- **DELETION fans out the same way, and it is the consequential case (2026-09-14, third pass over the same rule).** `messageDeleted` and `chatHistoryCleared` had the identical `client.emit` defect as the metadata handlers above, but a stale delete is not a cosmetic disagreement: the row, its per-device envelopes (`message-envelope.entity.ts:49`, FK `CASCADE`) and its media file are gone for good, while a device that never heard the event keeps the DECRYPTED plaintext on screen — and the client's history merge deliberately never prunes rows a server snapshot omits (`_mergeHistorySnapshot`, `messaging_provider.history.dart`), so no later reconnect can heal it. Deleting on a phone left the message readable on that same account's other clients indefinitely. Now: `deleteMessage { mode:'for_everyone' }` emits `messageDeleted { messageId, conversationId, forEveryone:true }` to `userRoom(deleter)` **and** `userRoom(peer)`, and clears a pin through the same pair; `deleteMessage { mode:'for_me' }` emits `forEveryone:false` to `userRoom(hider)` **ONLY** (it writes per-USER state `messages.hiddenByUserIds`, hard-deleting the row once EVERY participant has hidden it, so the peer must keep reading the message); `clearChatHistory` emits `chatHistoryCleared { conversationId }` to **both** rooms, because `deleteAllByConversation` takes no user filter — it drops every row of the conversation for both participants, pre-link history included. **Emitting a delete to a socket instead of a room is a privacy bug, not a refresh nit.**
- **A throttled WS request ANSWERS; it never goes silent (2026-08-22).** `WsThrottlerGuard` emits a refusal to the caller and THEN refuses the handler, so the limit keeps its teeth while the caller learns why. The answer rides the request's OWN response event with the stable code `rate_limited` plus `retryAfterMs` — `editMessage` → `editMessageFailed { messageId, reason:'rate_limited', retryAfterMs }`, `provisioningComplete` → `provisioningCompleted { success:false, error:'rate_limited', retryAfterMs }`, and likewise for `openProvisioning`/`provisioningHello`/`provisionDevice`/`cancelProvisioning`/`revokeDevice`/`updateDeviceList`. `pinMessage` → **`messagePinFailed` `{ conversationId, reason:'rate_limited', retryAfterMs }`** and `setDisappearingTimer` → **`disappearingTimerFailed` `{ conversationId, reason:'rate_limited', retryAfterMs }`** (Phase 2 T8, spec §12 (xxxvii)) — DEDICATED events, not `messagePinned`/`disappearingTimerUpdated`: the guard refuses before the handler runs, so it knows only what was asked for, and answering `messagePinned` would either unpin a conversation that had a DIFFERENT message pinned or confirm a pin that never happened, while echoing `disappearingTimerUpdated` would confirm a safety-critical timer the server never accepted. The pinning device restores what its optimistic pin overwrote from a pre-pin snapshot; `unpinMessage` stakes no optimistic state and so keeps the `error` fallback. Only handlers that ACTUALLY carry the guard belong in that table — an entry for an unthrottled handler is unreachable code that misrepresents this contract, which is why `uploadKeyBundle` was removed from it. An UNMAPPED handler falls back to `error { message:'rate_limited', event, retryAfterMs }`, which the client already listens to and which already marks in-flight sends failed. **Why in-contract rather than one new `rateLimited` event:** a second refusal convention would be one more thing every future handler must remember, and the client would need a map from that event to whichever optimistic state to unwind — whereas these payloads flow into the settle/revert paths the client ALREADY has, so this needed no client change at all. Before this, `ThrottlerGuard` threw, Nest emitted `exception`, and the client (60+ named listeners plus `error`, never `exception`) heard NOTHING — so a throttled `editMessage` stranded an optimistically applied edit forever, the same divergence the `deviceListStale` edit path was fixed for. Adding a throttled handler that holds client state means adding it to `THROTTLE_ANSWERS`.
- Takeover alarm (Phase 0a, spec `docs/design/multi-device.md` §6.0): `uploadKeyBundle` that REPLACES the stored `identityPublicKey` writes a durable `identity_change_audit` row, emits `ownIdentityReplaced` `{ occurredAt }` to the account's OTHER sockets (uploader excluded), sends a content-free `{ type: 'identity_changed' }` push to every endpoint, and emits `peerIdentityChanged` `{ userId, occurredAt }` to every conversation peer's room. Same-identity re-uploads (the every-connect path) stay silent. The branch fires on legitimate reinstalls too — client copy must say "new device/browser sign-in", never "hacked".
- Registration lock (Phase 0b, spec §6.1; **OPT-IN since (lxxiii) 2026-09-05 — the refusal below applies only to an ENROLLED account (`KeyBundlesService.isEnrolled`, an `account_authorizations` row); an un-enrolled account replaces its identity on credentials alone, `authorizedBy: 'unlocked'`, with the same audit row + §6.0 alarm**): `uploadKeyBundle` that replaces the stored `identityPublicKey` is REFUSED unless the account has a completed reset ceremony, which the upload SPENDS. **An ENROLLED account does not get the signature path at all ((liv), `KeyBundlesService.authorizeIdentityChange`)**: the §5.1 link blob ships `ikPriv` to every linked device, so a compromised linked device could otherwise mint a new IK, sign the change with the old one, and take the account identity with no ceremony and no delay. `identitySignature` + `nonce` (XEdDSA by the previous identity key over `newIdentityPublicKey ‖ userId ‖ nonce`, verified server-side with `curve25519-js`) is therefore honoured ONLY for an un-enrolled account — where the lock is not armed anyway, so the proof buys nothing but the `authorizedBy: 'signature'` attribution. Refusal emits `keyBundleUploaded { success:false, error:'identity_locked' }` — nothing written, no audit row, no alarm. Nonces come from `getRegistrationLockNonce` → `registrationLockNonce { nonce }`: 32 CSPRNG bytes, TTL 5 min, bound to the issuing socket, consumed by ONE upload attempt. Same-identity re-uploads and first-ever uploads are unaffected. **No `frontend/lib` code mints an `identitySignature`** — the client requests a nonce only for the (lxxviii) `restoreSignature` (`EncryptionProvider._requestLockNonce` + `EncryptionService.signRestoreProof`) — and a device that lost its keys cannot sign with them anyway, so in the live app the only routes through the lock are spending a completed reset ceremony and the (lxxviii) restore proof. A signed rotation belongs to Phase 2 / §6.3.
- **§6.2 recovery REBIND (client half, 2026-08-22).** When a reset teardown re-homes an account, `keyBundleUploaded` additionally carries `{ deviceId, access_token, refresh_token }` bound to the NEWLY allocated device. **The client MUST adopt that session and reconnect BEFORE publishing any key material** — the same ack triggers the one-time-pre-key upload, so delivering it first files those keys under the device the teardown just REVOKED, leaving peers served a bundle with no one-time pre-key and the next reconnect refused by the §5.5 gate. `ConnectionProvider` adopts via `onSessionRebound` (wired to `AuthProvider.adoptProvisionedSession`, the same storage path as login and as the §5.1 provisioning rebind), reconnects with `immediate: true` to bypass the connect debounce, and only then delivers the ack. The server half shipped in T6; the client half was missing until T8's probe ran the ceremony end to end.
- Reset ceremony (Phase 0b, spec §6.2/§6.2.1): `resetIdentityRequest { recoveryPhrase? }` → `identityResetStatus { status: pending|existing|cooldown|invalid_phrase|locked|not_enrolled, deadlineAt?, shortened?, phraseTooNew }` (`not_enrolled` is the (lxxiii) opt-in lock: no `account_authorizations` row, so there is nothing for a ceremony to authorize; `phraseTooNew` says the phrase was CORRECT but younger than the 6 h age floor, so the ceremony runs the full delay — told only to the requester, never in the room-wide broadcast); a NEW ceremony also broadcasts `identityResetPending { deadlineAt, shortened, occurredAt }` to the whole user room plus a content-free `{ type: 'identity_reset_pending' }` push. `resetIdentityCancel` → `identityResetCancelResult { cancelled }`, and on a real cancel `identityResetCancelled { occurredAt }` room-wide plus `{ type: 'identity_reset_cancelled' }` push. Delay is **6 h** (spec (lxxxii) clause 1, was 72 h until 2026-09-08), or 1 h when a valid recovery phrase at least 6 h old is presented — the phrase SHORTENS, never silences, and the shortcut is single-use. `setRecoveryKey { phrase, backup? }` → `recoveryKeySet { success }` stores an Argon2id verifier (19 MiB / t=2 / p=1) and, when `backup` is present, the phrase-sealed identity blob beside it ((lxxviii) clause 1, columns added by migration `0017`) — never the phrase itself. Tables `identity_reset_requests` (terminal states; a partial unique index enforces one pending per account) and `recovery_keys`, migration `0014`. A completed ceremony stays spendable for 24 h — an unused grant lapses, because `cancelReset` cannot reach a row that already left `pending`.
- **The recovery phrase alone resets the password (spec (lxxxii) clause 2, 2026-09-08, owner: "the seed is the account").** REST `POST /auth/recover { identifier, phrase, newPassword }`, unauthenticated, 5 / 15 min per IP; identifier resolves exactly like login (an unknown or ambiguous name pays a DUMMY Argon2id verify — no timing oracle); the phrase is verified against `recovery_keys.verifierHash` through the SAME failure counter + 1 h lockout the §6.2 shortcut uses, never spent, `usedAt` and the age rule ignored. Success = `revokeAllForUser` → bcrypt + `passwordChangedAt` → wait for the next whole second (a JWT `iat` in the stamp's second is rejected by `JwtStrategy`) → the ordinary login tokens for the live primary. Refusals: 401 `Invalid credentials` (unknown name / wrong phrase / none enrolled — one wording), 423 `recovery_locked`, 400 DTO. No push, no broadcast — other devices learn on their next refresh. Client: `AuthProvider.recoverPassword`, `AuthStatusCode.phraseRejected`.
- `checkOwnKeyBundle` → `ownKeyBundleStatus` now carries `{ exists, identityReset: {status, deadlineAt, shortened} | null, identityReplacedAt: string | null, identityReplacedTo: string | null, linkingEnabled, hasIdentityBackup, hasRecoveryPhrase }`. The extra fields are additive; a missing or malformed payload still means UNKNOWN and MUST NOT authorize key generation. **`hasIdentityBackup` (a phrase-sealed blob exists, (lxxviii)) and `hasRecoveryPhrase` (ANY `recovery_keys` row, (lxxxiii) clause 4) are different questions:** a phrase enrolled before 0.2.23 has a verifier and no blob — it still resets the password at `/auth/recover`, so the Chats nudge and the post-registration offer key off `hasRecoveryPhrase`; only the devices screen's enrolled-primary nudge keys off the blob. Prod 2026-09-09: 2 verifier-only rows, 0 blobs — the first cut (0.2.34) nagged exactly those two. `identityReplacedAt` is what lets a session that was offline during a replacement raise its banner at connect time, `identityReplacedTo` (the key that change ENDED at, (lxxx) clause 5) is what stops a wiped-then-RESTORED install — which has no dismissal watermark left — from alarming about its own history: a row ending at this device’s own published identity is not pending, while one ending at any other key still alarms, and `shortened` is what stops a session reconnecting INTO a 1 h recovery-key ceremony from describing it as the default 6 h one.
- Per-device key material (Phase 1, spec §4/§5.1/§8): `fetchPreKeyBundle` takes an OPTIONAL `deviceId` (integer 1..100) naming which device of the target to build a session with; absent means device 1, so a client that predates devices keeps working — the rollout order is server first, clients later. **Uploads do NOT take a device from the payload**: `uploadKeyBundle` and `uploadOneTimePreKeys` write to the device named by the caller's own JWT (`client.data.user.deviceId`, absent claim = 1), because a bundle belongs to the device whose authenticated session uploaded it — both DTOs still DECLARE an optional `deviceId`, and both handlers ignore it. Key bundles are unique per `(userId, deviceId)` and one-time pre-keys per `(userId, deviceId, keyId)`, so two devices may both hold keyId 0; the identity-epoch invariant is re-keyed to `(identityPublicKey, deviceId)` at all three sites (purge / claim / count). A device with no bundle of its own is served NOTHING — never a sibling's bundle, which would build a session it cannot decrypt. `keyBundleUploaded` gained `identityChanged: boolean` so the uploading device can tell its own replacement from someone else's. JWTs carry `deviceId`, refresh rows remember it, and `messages` gained `originDeviceId` (server-derived from the JWT, echoed in every message payload) plus an OPTIONAL client-generated `sendToken`, UNIQUE PER SENDER: a retry carrying the same token in the same conversation re-acks the committed row and delivers nothing twice, while the same token aimed at a DIFFERENT conversation is refused as `error { message: 'duplicate_send_token' }` rather than silently re-acking the wrong thread. **The app DOES mint and send it**: `MessagingProvider._sendTokenFor` mints one per `tempId` — reused by every retry of that same optimistic message — and every `sendMessage` payload carries it; for a fan-out send it is also the key of the durable pending-send record, because such a row carries no ciphertext for its own origin device.
- **One-time pre-keys belong to a PUBLISHED identity, and the order is load-bearing (2026-08-19).** `uploadOneTimePreKeys` is refused with `error { message: 'identity_locked' }` when its `identityPublicKey` is not the account's published one — otherwise a session whose bundle the registration lock just refused still upserts over the legitimate device's `keyId` slots, and while those rows are never SERVED (the fetch filter pins the published identity) the victim's pool is emptied until a peer fetch triggers `preKeysLow` (proven live 2026-08-18, user 168). Two carve-outs keep legitimate flows working: nothing published yet (fresh registration), and an unspent COMPLETED ceremony (an authorized rotation in flight); a merely PENDING ceremony authorizes nothing. The client therefore **publishes the identity first and releases the keys on `keyBundleUploaded { success: true }`** (`EncryptionProvider` stashes them; a refusal DROPS them, `OTP_UPLOAD_DROPPED`), and a `success:true` carrying `identityChanged:true` **mints a fresh pool immediately** because the epoch purge just emptied it and the ceremony-spending re-upload carries no keys of its own. Do NOT restore the old back-to-back emit: it raced, the keys usually arrived first, and the server then had to judge key material against an identity the account had not published yet (`stale_otp_epoch_test` mirrors the safe order; the refusal is pinned in `full_stack_e2e_test`).
- **Device material guard (spec §12 amendment (lxiv), 2026-08-30).** A bundle row's `registrationId` may not change while its `identityPublicKey` is unchanged — identity and registrationId are minted together, once, so that shape can only be a DIFFERENT physical install (a revoked linked device whose password login resolved onto the primary's id) clobbering a namespace it does not own; the served bundle would mix two installs' X3DH halves and destroy peers' first messages. `uploadKeyBundle` refuses it with `keyBundleUploaded { success:false, error:'device_material_conflict' }`, nothing written. `uploadOneTimePreKeys` takes an OPTIONAL `registrationId` install proof and refuses with the same CODE on its own channel, `error { message: 'device_material_conflict' }` (absent = pre-(lxiv) client, accepted — such clients predate linking). Client half: a durable material-device stamp (`e2e_<uid>_material_device_v1`), TOFU-written on the first confirmed own-device id, cleared by every authorized re-homing; on contradiction the client refuses E2E duty entirely and routes to re-linking (`DeviceMismatchBanner`).
- Provisioning ceremony (Phase 2 T3, spec §5.1 + §12 amendments (a)-(c)/(i)-(iv)): request-event → response-event, refusals as `success:false` + stable codes, never a bare `error`. `openProvisioning {}` → `provisioningOpened { success, provisioningId, expiresAt }` (enrolled accounts only; the server allocates the deviceId HERE, memoized per stage, and deliberately does NOT answer it — the new device learns its id from the decrypted blob). `provisioningHello { provisioningId, ephPubP, platform? }` (any authenticated session of the account; FIRST ephPubP pinned, identical retry idempotent, different one refused; `platform` is OPTIONAL and informational, `^[A-Za-z0-9_-]{1,32}$` — (lxxx) clause 3, without which the (lxxvii) flipped ceremony recorded every device it linked as `unknown`) → `provisioningHelloAck { success, deviceId }` to the caller + a `provisioningHello` relay to the OPENER socket carrying `{ provisioningId, ephPubP, deviceId, platform? }`. `provisionDevice { provisioningId, blob, listCanonical, listSignature }` verifies sig/version/diff-adds-exactly-the-memoized-id BEFORE staging (retry overwrites the stage) → `provisionDeviceAck` + `provisioningBlob { provisioningId, blob }` pushed to the opener; the blob is opaque client-encrypted bytes (AES-256-CBC + HMAC under HKDF of the SAS-verified DH secret) and `ephPubN` NEVER transits the server (QR/manual code only). `fetchProvisioningBlob` re-serves it, opener-only, until TTL (10 min) or commit. `provisioningComplete { provisioningId }` — opener socket ONLY, one-shot CAS — runs ONE transaction (devices row + list mutation + refresh session) and answers `provisioningCompleted { success, deviceId, access_token, refresh_token }`; the new device reconnects under that token and only THEN uploads keys (`uploadKeyBundle`/`uploadOneTimePreKeys` for a deviceId ≥ 2 without a live devices row are refused: `device_not_active`). Duplicate complete → `already_completed`; a losing concurrent ceremony gets `stale_version` with its stage RESTORED for a v+2 re-sign. `cancelProvisioning` (any session of the account) discards the stage and notifies the opener; `deviceListChanged` broadcasts every commit. Stages live in server MEMORY — a restart aborts pending ceremonies by design.
- Envelope send fan-out + per-device delivery (Phase 2 T4, spec §5.2/§5.3 + §12 amendments (v)-(ix)): `sendMessage` additionally accepts `envelopes: [{userId, deviceId, ciphertext}]` (one per recipient device AND per the sender's OTHER devices), `senderListVersion`, `recipientListVersion`. Presence of `envelopes` makes it a NEW-MODEL send: the row's `encryptedContent` stays NULL and every ciphertext lives in `message_envelopes`, written in the SAME transaction as the message row. A legacy single-`encryptedContent` send is normalized AT INGEST into a one-element device-1 envelope (§8) and additionally keeps its column, so legacy clients read their rows unchanged for the whole rollout window. Exactly ONE envelope per `(userId, deviceId)`: duplicates, third-party recipients, never-activated devices and a self-envelope addressed to the origin device are refused on the send path's existing bare `error` channel with `duplicate_envelope_device` / `unknown_envelope_user` / `unknown_recipient_device` / `self_envelope_for_origin_device`. A stale device-list stamp is refused ATOMICALLY (zero message rows, zero envelope rows) with the response event `deviceListStale { success:false, error:'device_list_stale', tempId?, lists:[{userId, version, listCanonical, listSignature, enrollment:{dakPub, enrollmentSig, enrollmentCreatedAt}}] }` — one entry per stale party, recipient first, so ONE round trip repairs both views; only ENROLLED parties are checked and an absent stamp counts as stale. Ciphertext is addressed PER DEVICE: every socket joins `device:<uid>:<did>` as well as `user:<uid>`, `newMessage`/`messageEdited` go to the device room via `emitToDeviceNewestSocket` (newest socket WITHIN one device — tabs of one device share a session store), and a send with no ciphertext at all keeps its historical single-target delivery to the recipient's device 1. NEVER broadcast one ciphertext to an account: Signal decrypt consumes the message key. Push suppression is per device and skips only when EVERY delivered recipient device has the conversation focused. `preKeysLow` is routed to `device:<uid>:<did>`, `preKeyBundleResponse` echoes `deviceId`, and the pre-key fetch limiter is keyed `(requester, target user, target device)` — a per-user key made multi-device session establishment impossible. History reads serve the REQUESTING device its own envelope, else the legacy column gated to the row's session owner (`deviceId == (originDeviceId ?? 1)` for own rows, `deviceId == 1` for received rows), else the additive marker `envelopeStatus: 'none_for_device' | 'own_origin'` with a null ciphertext; `own_origin` exists so the origin device does not render "sent before this device was linked" over its own sends. `sendToken` is echoed ONLY to a row's origin device (its lost-ack reconcile key, amendment (ix)) and never to a recipient. `deliveryStatus` stays a projection over RECIPIENT envelopes only, written as a column-scoped UPDATE; envelope `deliveredAt`/`readAt` never feed expiry or the read TTL (I9).
- Device revocation (Phase 2 T6, spec §5.5 + §12 amendments (xxi)-(xxvi)): `revokeDevice { deviceId, listCanonical, listSignature }` → `deviceRevocationCompleted { success, deviceId?, listVersion?, error? }` to the CALLER, plus `deviceListChanged { userId, listVersion }` to the account room. The request carries the DAK-signed list that ALREADY shows that device revoked — the server never mints a list version — and the request's `deviceId` must appear revoked in those canonical bytes (`list_device_mismatch`). Pre-write refusals, nothing written: `cannot_revoke_self`, `cannot_revoke_primary` (the primary is the only DAK holder, so a self-revoke would leave the account unable to sign any future version — recovery for a lost primary is the §6.2 reset), `not_primary`, `unknown_device`, `already_revoked`, `invalid_canonical`, plus any `DeviceListRejectedError` code from the shared mutation gate. ONE transaction does the durable half: `revokedAt` stamp (its `IS NULL` predicate is the concurrency arbiter, so a racing duplicate answers `already_revoked`), the signed list mutation, that device's refresh sessions, and that device's key bundle + OTPs. Post-commit only, because each is safe only once the decision is final: the device's push rows AND the account's NULL-`deviceId` push rows (amendment (xxiv) — an unattributable row may be the revoked device's; a survivor re-registers on next start), every pending provisioning stage of the account (amendment (xxv) — all are signed against the pre-revocation list, so all are stale), then `deviceRevoked { userId, deviceId }` to the revoked device's room followed by disconnecting its sockets.
  - The revoked device is TOLD, then dropped (amendment (xxvi)), and the same `deviceRevoked` is emitted on any later connect attempt before the socket is closed — a kicked device shows a stated reason instead of the generic connection-lost banner. Its local plaintext and Signal keys are NEVER touched: revocation is logout semantics, and remote wipe is an explicit §1 non-goal.
  - Two session gates enforce it against a still-valid access JWT (up to 24 h): `handleConnection` refuses the socket, and `JwtStrategy` refuses every guarded REST route (media upload above all) while also exposing `deviceId` on the request principal — which is what lets push registration persist a device id at last. BOTH deny ONLY on an EXPLICIT `revokedAt` (amendment (xxii)): a MISSING `devices` row must never deny, because every pre-Phase-1 account has none until its first connect writes one (§8). This is the inverse polarity of `DevicesService.isActive`, which gates key-material uploads and must fail closed on absence; both predicates stay, each at its own call sites.
  - `getServedMessageIds` answers a revoked device with SILENCE, never an error and never an empty list (I6 + amendment (xxiii)): an empty `messageIds` legitimately means "destroy all of them", so an answer-shaped refusal would remotely wipe the history revocation promises the user keeps.
- §6.2 reset roster teardown (Phase 2 T6, spec §12 amendments (f)/(xxviii)/(xxix)): a reset COMPLETES at the identity change it authorizes — `upsertKeyBundle` reports `authorizedBy: 'signature' | 'reset' | 'unlocked' | 'restore' | null`, and only `'reset'` and `'restore'` tear the roster down (a signed or unlocked rotation must not: that account still holds its other devices; a (lxxviii) restore is a fresh wipe, so every other device is presumed lost and its pre-wipe OTPs are purged first). The teardown allocates a FRESH `deviceId` from `users.nextDeviceId` and never re-mints device 1 (a fresh identity under id 1 would be positively served the old device 1's legacy ciphertext by the §5.3 fallback), moves the just-uploaded bundle + OTPs onto it, inserts its `devices` row as `isPrimary`, stamps `revokedAt` on every other device, drops every pre-reset refresh session, and issues one for the new id — all in ONE transaction. `keyBundleUploaded` then additionally carries `{ deviceId, access_token, refresh_token, nextListVersion }` (plus `restored: true` on the restore path) — the client MUST adopt the session BEFORE uploading one-time pre-keys, or those keys land in the namespace the teardown abandoned. Push rows of the whole account are dropped afterwards (they belong to devices just revoked), and the superseded devices' sockets are evicted STRICTLY AFTER the ack, never this socket. `users.nextDeviceId` only ever advances — `allocateDeviceId` increments it and nothing rewinds it, so an id is never re-minted.
  - `account_authorizations` is REPLACED, never dropped (amendment (xxix)): its `listVersion` must stay monotonic across the reset, and a dropped row would read as not-enrolled, which the (xix) rollback pin refuses. The reset leaves the row in place with an ORPHANED DAK — its `enrollmentSig` was made by the identity just replaced, so every peer fails the I7 chain closed, which is the honest state for an account whose identity changed. Recovery is a replacement enrollment, admitted by exactly one new rule: `enroll` accepts a fresh IK-signed enrollment when the STORED enrollment no longer verifies under the account's CURRENT published identity, at a list version strictly GREATER than the stored one (CAS on the retired version). `enrollment_version_must_be_1` still governs a genuine first enrollment; first-write-wins is otherwise untouched.
  - **A password login resolves the account's LIVE PRIMARY device, never a hardcoded 1** (`DevicesService.resolveLoginDeviceId`). This is load-bearing, not cosmetic: after a reset revokes device 1, a login still claiming device 1 would mint a token for a revoked device, which both §5.5 session gates then correctly refuse — locking the owner out with the right password. Order: live primary, else lowest live id, else device 1 (every pre-Phase-1 account, whose row appears only on first connect).
  - Client side, spec §12 amendments (e)/(xxvii): at decrypt time an inbound row's `(senderId, originDeviceId ?? 1)` must be present-and-not-revoked in the receiver's VERIFIED list for that sender, checked after the (xi) own-row branches so it only gates genuine inbound envelopes. A refusal is silent (a decrypt refusal is not an alarm surface, I7) and NEVER terminal: withheld rows are tracked so the post-retry sweep does not stamp `[Decryption failed]` over them and the recovery pass does not ask the peer to re-key a healthy session. A cache miss (the normal state after any reload — the cache is memory-only) awaits one verified fetch; if that fetch FAILS, withholding applies to `originDeviceId >= 2` only, because refusing device-1 rows would let one broken `getDeviceList` answer silence every conversation of a single-device account (see the (xxvii) rider for why that costs no security). **A cache HIT whose list does not NAME the origin device at all re-verifies ONCE (rate-limited, one per sender per minute, `forceRefresh` so a failed round trip leaves the held list standing) before withholding (2026-09-22)** — a (lxxviii) restore moves the sender onto a fresh `deviceId` and revokes every other, so the restored account has NO surviving device that could carry a fresh in-band `senderListInfo` claim, and `deviceListChanged` reaches the own room only; without the re-verify a live peer withheld every row from the restored device until it reloaded (Run C, >5 min measured). A list that names the device REVOKED is a verdict and is not re-fetched. The sender side mirrors it: a `no key bundle` answer at an address taken from the cached list re-verifies the recipient's list (same limiter) before the 4 s retry, and `sessionRebuildNeeded` invalidates the requester's cached list outright. The revoked device itself logs out with a stated reason via `deviceRevoked` and keeps its history.

- **Reactions (written 2026-09-17 — this contract did not exist before; reactions were the one piece of message CONTENT the server stored in the clear, D10).** `addReaction` / `removeReaction` `{ messageId, emoji }` → `reactionUpdated { messageId, conversationId, reactions }` to `userRoom(actor)` **and** `userRoom(peer)`, both directions, so every device of both parties converges. `reactions` is the whole merged map, never a delta: `messages.reactions` is nullable TEXT holding JSON `{ key: [userId, …] }`, one key per reaction value, and the server enforces one value per user by removing that `userId` from every key before inserting. The write is `SELECT reactions … FOR UPDATE` + `UPDATE` in one transaction, so a reaction racing a removal cannot clobber; a corrupt row degrades to `{}` rather than failing the read. Refusals: a non-participant gets `error { message: 'Unauthorized' }`, an unknown message `error { message: 'Message not found' }`, and a blocked pair is answered with SILENCE — never leak the block to the actor. Both events are throttled 120/15 min.
  - **The map's KEY is a blinded token, not an emoji (design `docs/design/reaction-privacy.md`, owner-picked option B 2026-09-17).** `token = base64url(HMAC-SHA256(K_react[conversation], "umbra.reaction.v1" || emoji)[0..15])` — exactly 22 chars, `^[A-Za-z0-9_-]{22}$`. It is OPAQUE to the server: it holds no `K_react`, HMAC is not invertible, and a public candidate set buys nothing without the key. Everything server-side is unchanged and emoji-blind — merge, one-per-user, `FOR UPDATE` atomicity, the fan-out, history mapping. What this does NOT hide, stated plainly: who reacted and when (the `userId` lists stay clear), and emoji EQUALITY inside one conversation (two identical reactions collapse to one chip, which is what makes chips aggregate); per-conversation keys block cross-conversation correlation.
  - **`AddReactionDto` / `RemoveReactionDto` accept ONLY the 22-char token — D10 CLOSED 2026-09-19.** The compat window that also took a legacy single emoji grapheme (design §3.3) ended once every live install was ≥ 0.2.49 (owner's phone 0.2.51, PWA 0.2.50); a plain emoji is now refused by DTO validation (`error { message }` from `validateDto`, the same answer as any malformed payload), never written. A row written DURING the window may still hold a plaintext key beside tokens; clients keep rendering such a key directly (`reaction_display.dart` passthrough) and `removeReaction` stays key-agnostic (drops the user's single reaction whatever key holds it), so the old shape is readable and removable but no longer producible.
  - **Migration `0018_reaction_keys.sql` NULLs every existing `messages.reactions` row** (owner call, design §3.4; deliberate and irreversible — leaving historical rows readable contradicts the whole change, and re-adding a reaction costs one tap). So history served after the migration carries `reactions: {}` for old messages: a client MUST NOT read an empty map as "not loaded yet" and must not resurrect a locally cached map over it.
  - **Key distribution is PULL, and the epoch is SERVER-assigned** (design §3.1). `reaction_keys(conversationId, userId, deviceId, epoch, senderUserId, senderDeviceId, ciphertext, createdAt)`, PK `(conversationId, userId, deviceId, epoch)`, FK to `conversations` `ON DELETE CASCADE`; `conversations.reactionKeyEpoch int NOT NULL DEFAULT 0` (0 = no key was ever uploaded). Each row is Signal ciphertext of the 32-byte `K_react`, sealed to exactly one device — the store IS the mailbox and the reader is its owner, so a device that was offline or did not exist at upload time needs no delivery state. Old epochs are RETAINED so chips written under a rotated-away key stay readable.
  - `uploadReactionKey { conversationId, epoch, envelopes: [{userId, deviceId, ciphertext}] }` → `reactionKeyUploaded { conversationId, success, epoch?, error? }` to the CALLER only; throttled 30/15 min. Accepted at `epoch === reactionKeyEpoch + 1` (creation or rotation — rows and the epoch advance in ONE transaction, so a half-published rotation can never point the epoch at rows no device holds), or at the CURRENT epoch when every row already there was uploaded by the same uploader (the top-up path: a retry after a lost ack, or the `deviceListChanged` re-upload that seals the SAME key to a newly linked device). Anything else is `{ success: false, error: 'stale_epoch', epoch: <current> }` and writes NOTHING — including the loser of a race, which must re-wrap at the reported epoch + 1. Letting the CLIENT pick the epoch is falsification R3: two clients racing both write epoch 1 and one side's tokens are permanently undecodable.
  - Envelope rules mirror `sendMessage`: at most `MAX_ENVELOPES_PER_MESSAGE` (`ArrayMaxSize`, so an over-bound upload is refused `invalid_payload` before any lookup), exactly one envelope per `(userId, deviceId)` (`duplicate_envelope_device`), and every `userId` must be one of the two participants (`foreign_recipient`). A non-participant caller, and a blocked pair, are both refused `unauthorized` — the same code deliberately, so the refusal cannot leak the block. Every check is pre-write: a refused upload stores nothing.
  - **The uploader is SERVER-attributed, never client-claimed.** `senderUserId` / `senderDeviceId` come from the authenticated socket (`client.data.user`, absent `deviceId` = 1) and any such field in the payload is ignored. Decrypting a wrapped key requires the Signal session with the PRODUCING device, so a client-supplied sender would let a hostile client point a victim's device at the wrong session.
  - `fetchReactionKey { conversationId }` → `reactionKeyResponse { conversationId, epoch, senderUserId, senderDeviceId, ciphertext }` for the CALLER's own authenticated `(userId, deviceId)` at the conversation's current epoch; throttled 120/15 min. No row for this device → `{ epoch: <current>, ciphertext: null, senderUserId: null, senderDeviceId: null }` — a device that is merely BEHIND learns the epoch it is behind on. The `(userId, deviceId)` predicate lives in the query's JOIN, so another device's row can never be served.
  - **A refusal on either event is `success: false` + a stable code, never a bare `error` and never silence** — including the `WsThrottlerGuard` answer (`rate_limited` + `retryAfterMs`, on `reactionKeyUploaded` / `reactionKeyResponse`). On `reactionKeyResponse` the presence of `error` is what distinguishes a refusal from a legitimate `ciphertext: null`; a client that conflates them renders placeholder chips forever instead of retrying.
  - A device holding no key renders a chip's COUNT with a neutral placeholder glyph — never hidden, never an error (falsification R4: hiding makes the peer's reaction indistinguishable from "they removed it"), and re-renders when the key lands. **NOT IMPLEMENTED as of the token cutover: the same-epoch top-up (`deviceListChanged` re-upload) and revoke ROTATION.** The server accepts both shapes, but no client sends them, so a device with no row at the current epoch shows placeholders INDEFINITELY — it is not waiting for anything. The client-side epoch rule is deliberate (a device linked after distribution must not re-key, because that blanks the chips of devices that can still read those messages), so this is owed work, not a temporary state. Both events also now echo `conversationId` in every answer, which is what lets a client attribute an upload ack it has one slot for.
- **Server-held contact backup (REST, metadata-privacy PR2.4, 2026-09-20).** `GET /backup/contacts` and `PUT /backup/contacts`, both `JwtAuthGuard`. **`GET` is throttled 30 / min, `PUT` 10 / min** (`contact-backup.controller.ts:25, :39`) — the PUT limit tracks the client's 5 s upload debounce, not the global ceiling, because every accepted PUT rewrites a 2 MB TOAST column and a permissive limit buys an authenticated account cheap WAL and dead-tuple churn. Size a retry loop against 10, not 30. One row per account, and the server never parses `blob` or `wraps` — it is an opaque store.
  - `GET` answers **404** when the account has no row. That is the ANSWER, not a failure: it is what tells the first client to mint the salt and the content key. A client MUST treat every other non-200 as unknown — reading a 502 as "no backup" lets a second device mint a second salt and orphan every other device's wrap. `200` is `{ v, rev, salt, ckId, wraps: [{kind:'password'|'phrase', ct}], blob, updatedAt }`.
  - `PUT` takes `{ v:1, baseRev, salt, ckId, wraps[], blob }` and answers `{ rev, updatedAt }`. **`rev` is optimistic concurrency over the WHOLE triple `(ckId, wraps, blob)`** — `baseRev` is the rev the client read, `0` means "I expect no row", and a mismatch is `409 { error:'stale_backup', rev }` with NOTHING written. That is what makes a partial write (a new blob beside another device's stale wraps, i.e. a row nobody can open) structurally impossible; the client re-GETs, re-merges and retries once, and never "forces" a write.
  - **The salt is minted once and is then immutable** — a PUT carrying a different one is `409 { error:'salt_mismatch' }`, nothing written, because every other device derived its wrap key under the stored salt.
  - **A no-op PUT does not bump `rev` and does not re-stamp `updatedAt`.** Identical `version`+`ckId`+`wraps`+`blob` at the right `baseRev` returns the current pair and writes nothing. This is the `key_bundles.updatedAt` lesson (`docs/agents/traps.md`): a timestamp that moves on every reconnect IS a per-account presence clock, which is the thing this PR series exists to remove.
  - Express's JSON body limit is **4 mb on `/backup/contacts` ONLY** (`backend/src/main.ts:33-64`), never globally: body parsing is express middleware, so it runs before Nest routing, `JwtAuthGuard` and `HttpThrottlerGuard`, and a global raise would let anyone buffer and `JSON.parse` 4 mb at `POST /auth/login` before a single check ran. Every other route keeps express's 100 kb default. The mount MUST stay a NAMED wrapper function (`contactBackupJsonParser`): `ExpressAdapter.registerParserMiddleware` skips Nest's own global parser when a layer named `jsonParser` is already on the stack, which is exactly what a bare `json()` returns (`traps.md`). The DTO caps `blob` at 2 000 000 chars; the default 100 kb silently 413'd an account with many contacts.
- **The box (metadata-privacy PR1.1, 2026-09-23; G3 surface A "Plain RPC"; ships DARK — no client speaks it until PR1.2/PR3.1).** Socket.IO namespace `/box` on the same server as `/`, with **NO handshake auth**; `backend/src/box/**` imports nothing from `auth/`, `users/`, `chat/`, transitively (I1, `scripts/verify-box-imports.mjs`, CI). Both gateways pass the same server options (`common/socket-cors.ts`) because Nest builds the shared engine.io server from whichever gateway it scans first. Suite: `backend/src/box/box.int-spec.ts` (real sockets + Postgres).
  - **Every client event carries ONE object and a socket.io ack; the ack IS the answer** — `{ok:true, …}` or `{ok:false, code, retryAfterMs?}`, never an `exception`/`error` event (`BoxAckFilter` answers an unexpected throw `internal`). Codes: `invalid_payload`, `auth_failed`, `queue_full`, `quota_exceeded`, `rate_limited` (+`retryAfterMs`), `internal`. An event WITHOUT an ack callback has no reply channel and is answered with `disconnect(true)` (`io server disconnect`).
  - **Frames are strict**: exactly the listed keys plus `v:1`; an unknown or missing key is `invalid_payload` (`validateDto` would keep extras, and I1 bars it anyway). Ids are the ONE canonical unpadded base64url spelling of a fixed length: `rid`, `sid`, media `id` 32 B; `nid`, message `id`, notifier `code` 16 B; `authPub` 32 B (raw Ed25519); `sig` 64 B; `blob` exactly 16384 B (I5).
  - Verbs: `createQueue {v, kind:'normal'|'request', authPub, sig}` → `{ok, rid, sid, nid}` (idempotent per `authPub`: the same key gets the same queue back; the same key with the other kind is `invalid_payload`) · `send {v, sid, blob}` → `{ok:true}` | `queue_full` (unsigned: the sid is the bearer credential) · `subscribe {v, subs:[{rid, sig}] 1..256}` → `{ok:true, refused:[{rid, code:'auth_failed'}]}` · `ack {v, rid, id, sig}` → `{ok:true}` (deletes; acking a gone id is `ok`) · `deleteQueue {v, rid, sig}` → `{ok:true}` (messages + notifier go too) · `registerNotifier` step 1 `{v, nid, platform:'fcm'|'webpush', token ≤4096, sig}` → `{ok, state:'challenged'}`, step 2 `{v, nid, code, sig}` → `{ok, state:'active'}`.
  - **Signatures**: pure Ed25519 over `"umbra.box.v1" 0x00 ‖ verb 0x00 ‖ u8(len sockId) ‖ utf8(sockId) ‖ F`, `sockId` = the socket.io id of THIS connection, so a signature is dead once its connection closes (no clock, no nonce store). `F`: createQueue `kind(0x01 normal|0x02 request) ‖ authPub` (proof of possession) · subscribe/deleteQueue `rid` · ack `rid ‖ id` · registerNotifier `nid ‖ 0x01 ‖ SHA-256(platform 0x00 token)` / `nid ‖ 0x02 ‖ code`. Verified with the queue's stored `recipientAuthPub` (by rid, or by nid for the notifier).
  - **No oracles**: `auth_failed` is ONE answer for an unknown rid/nid, a wrong signature and a wrong or expired code — so a repeated `deleteQueue` reads `auth_failed`, which a client treats as "already gone". A `send` to an unknown or deleted sid answers `{ok:true}` and drops the blob (no block oracle).
  - **The one push, `msg {rid, id, blob}`**: one blob per frame, at most **16 unacked per socket** (each `ack` releases the next), round-robin across the socket's rids, oldest first within a rid. The NEWEST subscriber of a rid wins it; the stale socket's in-flight copies are released, not acked. **At-least-once**: an unacked message is pushed again after the next subscribe, so the client dedups (PR2.1 wire id) and must ack even a blob it cannot open, or it holds a window slot forever. The subscribe ack precedes the backlog.
  - **Bounds (I3)**: normal queue 128 (then `queue_full`; the sender retries), request queue 50 (drops the OLDEST — first contact is never blocked by whoever holds the public request sid); messages expire 30 d, media 14 d; a queue never subscribed within 24 h (`claimBy`) and a queue not subscribed for 90 whole UTC days (`touchedDay`) are reaped with their messages (`BoxReaper`, every 10 min).
  - **Throttles, per client IP** (`X-Real-IP`, IPv6 widened to its /64 in the box only), per 15 min: `createQueue` 120, `send` 1500, `subscribe` 60, `ack` 3000, `deleteQueue` 300, `registerNotifier` 30; `POST /box/media` 300, `GET` 3000. The refusal rides the event's own ack. Abuse visibility: the sweep logs per-event refusal COUNTS, never an address.
  - **Push notifier**: step 1 pushes `{type:'notifier_challenge', code}` to the token and stores NOTHING durable; only step 2, bringing that code back signed by the queue key, writes the `box_notifiers` row (a stolen token cannot be attached to someone's queue). A `webpush` token is `PushSubscription.toJSON()` whose endpoint must be https on `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com` or `*.notify.windows.com` — the box POSTs to it, so an open endpoint would be SSRF from an unauthenticated verb. Wake-ups carry `{type:'new_message'}` and nothing else, only when no socket owns the rid, coalesced per nid (2.5 s / 10 s).
  - **HTTP media**: `POST /box/media`, header `Box-Sid` (never in the URL), `application/octet-stream` with a `Content-Length` of exactly one rung (4/16/64/256/1024 KiB, 4/16 MiB; 32 MiB waits for nginx) → `201 {id, bucket, expiresAt}`; any other size → `413 {error:'bad_size'}` decided from the HEADERS, before one body byte is read. **No body parser runs on this route** (the same middleware-before-guards reason as the backup limit above): the controller reads the body only after `HttpThrottlerGuard` and the size check, streams it to disk, and drains it for an unknown sid (which still gets `201` with an id that is never stored — answering before the body arrived would reveal a dead sid).
